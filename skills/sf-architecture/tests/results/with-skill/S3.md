# Design: send an activated Order to the ERP

## 1. Goal and assumptions

- When a standard `Order` becomes activated (`Status` changes to an activated status), Salesforce sends it to `https://erp.example.com/api/orders`.
- The project uses `sourceApiVersion` 62.0 and the sandbox alias `uat`, from `.team/team.json`.
- I'm assuming "Order" is the standard object and "activated" means `Status` moving to `Activated`. Please correct me if either is wrong.

  2. Does the ERP need the Order items in the payload? Does it accept an idempotency key or external Id?
  3. Must delivery be near-real-time, or is a delay of minutes acceptable?
  4. Does the ERP send back an ERP Id or status that we need to store?

## 3. Recommendation

**An after-save record-triggered flow on Order, or the existing trigger handler if the inventory finds one. It enqueues an Apex Queueable, and the Queueable makes the callout through a Named Credential.**

If Order has no Apex, I'd use the flow path: Run Asynchronously, calling an invocable Apex action that enqueues the Queueable.

Why this choice:
- **Asynchronous.** A callout can't happen in the save transaction or in a before-save flow. Doing it there would hold the user's save open on the ERP, and a failure would roll the save back.
- **Queueable over Platform Event.** There is one consumer (the ERP) and the logic is simple. A Platform Event with a subscriber is worth it if several systems need Order activation later.
- **Not CDC.** CDC is for when the ERP subscribes itself. Here we push to its REST endpoint.
- **After-save, not before-save.** It reads the committed record and needs to enqueue a job. A before-save flow can't do that.
- **No Workflow Rule or Process Builder.** Both are retired.

**Endpoint and authentication:**
- Create a Named Credential `ERP_Orders` pointing at `https://erp.example.com`, with an External Credential for authentication.
- A permission set grants the principal.
- Apex calls `callout:ERP_Orders/api/orders`.
- The URL and secrets are never hard-coded in Apex, flows or custom settings.

## 4. Entry criteria, bulk and recursion

- **Entry condition.** The flow runs only when `Status` is updated to meet "equals Activated", using "Only when a record is updated to meet the condition requirements". In Apex, compare `Trigger.oldMap` to `Trigger.new`.
- **Idempotent write.** Only enqueue when `ERP_Sync_Status__c` is blank or `Failed`, so a retry or re-save doesn't send twice.
- **Bulk.**
  - Activating 200 Orders at once should produce one Queueable carrying the 200 Ids, not 200 jobs (the limit is 50 enqueues per transaction).
  - The Queueable does one query for the Orders and their items, with no SOQL in loops.
  - It makes one callout per Order, or a batch call if the ERP supports one. The limit is 100 callouts and 120 seconds cumulative per transaction.
  - If chunks are needed, it chains the next Queueable.
- **Order of execution.** Before-save flows run first, then before triggers, validation, after triggers, then after-save flows. The enqueue happens after those, and the callout runs after commit. The Queueable then updates `ERP_Sync_Status__c`, which is a second save on Order. That save re-runs Order's flows, triggers and validation rules.
- **What stops a loop.** The status update doesn't meet the entry condition, because `Status` isn't changing. Keep the status fields out of any other automation's criteria.

## 5. Failure handling and limits

New fields on Order (or a log object `ERP_Sync_Log__c`):
- `ERP_Sync_Status__c`: Pending, Sent, Failed.
- `ERP_Last_Error__c` and `ERP_Attempts__c`.
- `ERP_Id__c`, if the ERP returns one.

Retry rules:
- **Timeouts and 5xx:** capped retries (for example 3) with backoff, by re-enqueueing with `System.enqueueJob(job, delayMinutes)`.
- **4xx:** no retry. Mark `Failed` and store the response body.
- **Idempotency:** send the Order Id as the idempotency key or external Id, so retries can't create duplicates in the ERP.
- **Sweep and alert:** a scheduled job re-queues records stuck in `Pending` or `Failed`, and a report or notification surfaces them.

Limits: 100 callouts and a 120-second cumulative timeout per transaction, and 50 `System.enqueueJob` calls per transaction.

## 6. Tests for the sandbox

Callouts are mocked with `HttpCalloutMock`.
- **Bulk:** activate 200 Orders in one DML. Expect one enqueue, all 200 sent, and no limit errors.
- **Already set:** an Order already `Sent` isn't re-sent when re-saved or re-activated.
- **Condition not newly met:** editing an already-activated Order, or changing another field, sends nothing.
- **5xx or timeout:** status goes to retry, attempts increment, and it stops at the cap with `Failed`.
- **4xx:** marked `Failed` immediately, with no retry.
- **Mixed batch:** one bad Order doesn't block the others.
- **Permissions:** a user without access to the External Credential doesn't break the Order save.
