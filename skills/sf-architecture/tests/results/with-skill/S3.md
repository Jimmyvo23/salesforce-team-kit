## 3. Recommendation

**Use an after-save record-triggered flow on Order. It calls invocable Apex on its Run Asynchronously path, and that Apex enqueues a Queueable with `Database.AllowsCallouts`. The callout goes through a Named Credential and External Credential.**

The flow is the entry point and the Queueable does the callout. If the inventory shows an Order trigger, I'd skip the flow and enqueue from the handler instead.

Why this choice:
- **No synchronous callout in the save transaction.** A callout in a trigger or before-save flow isn't allowed, and you can't call out with uncommitted work pending. The async path runs after commit, so the ERP only sees committed data.
- **Why not before-save.** It can't make callouts or touch other records. Updating the sync status on the same Order from the async job is a separate transaction.
- **Why Queueable over the alternatives:**
  - It is monitorable and chainable for retries, and it takes non-primitive parameters. `@future` offers none of that.
  - A Platform Event adds a subscriber and only pays off with several consumers.
  - Change Data Capture fits only if the ERP subscribes itself over Pub/Sub API. Say so if it can. That removes the outbound code, but you lose control of the payload shape and the retry logic.
- **Credentials.** Endpoint and auth live in a Named Credential plus External Credential, with a permission set granting the principal. Code calls `callout:ERP/api/orders`. The URL and secrets are never hard-coded in Apex, flows or custom settings.
- **Run context.** The flow runs in system context without sharing. The Queueable should be `with sharing` or `inherited sharing` on purpose. Because it writes status back to Orders the user may not edit, state that it runs in system mode.

## 4. Entry criteria, logic, bulk, order of execution

- **Entry condition.** Fire on the change, using "Only when a record is updated to meet the condition requirements". The condition is `StatusCode = Activated` AND `Sync_Status__c` is blank or `Failed`. This also covers Orders created already activated, if the flow runs on create and update. Confirm whether you want that.
- **Idempotent target.** The ERP call carries the Order Id as an idempotency key or external Id. If the ERP supports upsert by external Id, use it.
- **New fields on Order:**
  - `Sync_Status__c`: Pending, Sent, Failed
  - `Last_Sync_Error__c`
  - `Sync_Attempts__c`
  - `ERP_Order_Id__c` (if the ERP returns one)
- **Bulk.** Records arrive in chunks of up to 200. The flow passes the collection of Order Ids to one invocable call, which enqueues one Queueable per chunk. It does no SOQL or DML in loops. The Queueable queries Orders and items once and sends them one at a time, or in batches if the ERP has a bulk endpoint. A 200-Order activation would otherwise need 200 callouts, over the limit of 100 per transaction, so the job must chunk its work. Process up to about 90 per run and re-enqueue the remainder.
- **Order of execution.** The flow runs at the after-save flows step, after before-save flows, before triggers, validation, the save and after triggers. The async path then runs post-commit, in its own transaction.
- **Recursion.** The status write-back is an Order update, so it re-runs Order flows, triggers and validation rules. The entry condition stops a loop, because `Status` hasn't newly become Activated and `Sync_Status__c` is no longer blank. Bulk-activating 200 Orders can still enqueue many jobs. The 50-enqueue limit per transaction is why the flow enqueues one job per chunk.

## 5. Failure handling and limits

- **Status tracking.** Set `Sync_Status__c = Pending` at enqueue and `Sent` on a 2xx response. On failure, set `Failed` and write the error to `Last_Sync_Error__c`.
- **5xx and timeouts.** Retry up to 3 to 5 times with backoff. A Queueable can't sleep, so use a chained job with a delay, or a scheduled sweep.
- **4xx.** No retry. Mark `Failed` with the response body, because the data needs a fix.
- **Duplicates.** The idempotency key stops a retry from creating a duplicate ERP order.
- **Alerting.** A scheduled sweep (scheduled flow or Schedulable Apex) retries `Failed` and stuck `Pending` Orders. It also notifies an admin or posts a report. If you need a full audit trail, add an integration log object.
- **Limits:**
  - 100 callouts per transaction
  - 120-second cumulative callout timeout
  - 50 `System.enqueueJob` calls per transaction

## 6. Sandbox test cases

1. **Single activation.** Draft → Activated sends one callout and sets `Sync_Status__c = Sent`. Use a mock `HttpCalloutMock` in Apex tests.
2. **Bulk.** Activate 200 Orders at once. All are sent, none exceed callout limits, and no `UNABLE_TO_LOCK_ROW` appears.
3. **Already set.** Re-saving an activated Order with status `Sent` doesn't re-send.
4. **Condition not newly met.** Editing other fields on a Draft or already-activated Order doesn't fire.
5. **ERP 500.** Retries up to the cap, then `Failed` with the error recorded.
6. **ERP 400.** No retry, `Failed` immediately.
7. **Timeout.** Treated like a 5xx.
8. **Retry after success.** A retried request with the same idempotency key doesn't duplicate (verify against the ERP's sandbox).
9. **Sweep.** The scheduled job picks up `Failed` Orders.
10. **Non-editing user.** A user without edit access on Order can activate and the status write-back still works.
