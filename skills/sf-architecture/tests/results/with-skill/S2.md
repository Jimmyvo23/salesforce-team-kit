# S2: Same-record field (with-skill)

## Recommendation: a before-save record-triggered flow on Opportunity (provisional)

### 1. Goal and assumptions
- On Opportunity save, set `Next_Step_Date__c = CloseDate − 7 days`. It writes only to the same record.
- Assumption: `Next_Step_Date__c` is a Date field. If it's a DateTime, say so, because the formula changes.
- Question for you: should it recalculate whenever `CloseDate` changes, or only fill the field when it's blank? That would overwrite a date a rep entered by hand. I've assumed it recalculates on a `CloseDate` change and on create. Say if you want something different.
- Target is the sandbox `uat` (from `.team/team.json`), API version 62.0 (from `sfdx-project.json`).

**What would change the recommendation:**
- An existing Opportunity Apex trigger means the logic goes in its handler's before-update/insert logic, with no new flow and no second trigger.
- Existing before-save flows mean mine gets an explicit `TriggerOrder`. If another one also sets `Next_Step_Date__c` or `CloseDate`, mine must run after it.
- An active Process Builder process or workflow rule that writes `Next_Step_Date__c` or `CloseDate` is a conflict. It should be migrated, not added to.
- A validation rule on `Next_Step_Date__c` could reject the computed value, for example if it must not be in the past.

### 3. Why a before-save flow
- The change sets a field on the same record being saved, so a before-save flow is the right tool. It needs no extra DML and no second save.
- An after-save flow would re-run the whole save order on the same record. Apex would add code and tests for no gain.
- A formula field isn't enough if users need to edit the date or report on a stored value. If it's display-only, a formula (`CloseDate - 7`) is simpler and needs no automation. Tell me if that's all you need.
- Before-save flows can't touch other records. That doesn't matter here, because nothing else is written.

### 4. Design
- **Trigger:** Opportunity, "A record is created or updated", before save, optimized for fast field updates.
- **Entry condition:** `CloseDate` is not null, and either the record is new or `CloseDate` changed. Use "Only when a record is updated to meet the condition requirements" so it doesn't fire on every save.
- **Logic:** one Assignment sets `$Record.Next_Step_Date__c = {!$Record.CloseDate} - 7`. Date arithmetic in flows works in days.
- **Idempotent:** the same `CloseDate` always gives the same result. If you want to protect manual edits, add a condition that the field is blank or equals the old `CloseDate − 7`.
- **Bulk:** the flow does no queries and no DML. 200 Opportunities in one load are just 200 assignments.
- **Recursion and order:** it runs first in the order of execution, before before-triggers and validation rules. It writes no other record, so nothing can loop.
- **Order:** give it an explicit `TriggerOrder` that fits the inventory results.

### 5. Failure handling and limits
- There are no callouts and no related-record writes, so the main risk is a validation rule rejecting the value.
- A null `CloseDate` can't happen if the field is required, and the entry condition guards it anyway.

### 6. Sandbox tests
- **Bulk:** insert 200 Opportunities with varied `CloseDate` values. All get `CloseDate − 7`.
- **Change:** update `CloseDate` on an existing record. `Next_Step_Date__c` moves with it.
- **Not newly met:** update an unrelated field. `Next_Step_Date__c` stays untouched, including a manual edit.
- **Boundaries:** a `CloseDate` on the 1st to 7th of a month, to check the month and year rollover.

### 7. Components for the change set
- Flow: `Opportunity_Set_Next_Step_Date` (name is a suggestion).
- Field `Opportunity.Next_Step_Date__c`, if it isn't already in production.
- Field-level security or permission set access, if the flow runs in user context.
