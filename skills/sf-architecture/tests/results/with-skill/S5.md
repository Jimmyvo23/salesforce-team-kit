# S5: Lookup or master-detail (with-skill)

**Recommendation: use a Lookup to Account, not master-detail.** This is provisional until you run the automation inventory below. API version is 62.0 and the sandbox alias is `uat`, from `.team/team.json`.

## 1. Goal and assumptions
- `Invoice__c` is a new custom object with about 2M records, and some Accounts will have over 100,000.
- I'm assuming invoices are loaded or synced in bulk, for example from an ERP. Tell me if that's wrong.
- I don't know whether you need roll-ups such as total invoiced or open balance on Account. That's the main open question.

Also check:

- **Existing Invoice objects:** run `SELECT Id, DeveloperName FROM CustomObject WHERE DeveloperName = 'Invoice'` with `--use-tooling-api`.

The inventory would change the recommendation in these cases:
- **An Account trigger already exists:** any invoice-to-Account logic goes in that trigger's handler, not in a new trigger.
- **Heavy Account flows or validation rules:** a rule that fires on every Account save makes parent locking worse, because each invoice load would touch the Account.

## 3. Why lookup
| Point | Master-detail | Lookup |
|---|---|---|
| Sharing | Inherited from Account | Invoice has its own OWD |
| Ownership | No owner | Has an owner |
| Cascade delete | Always | Optional |
| Roll-ups | Native | Not native |

**Volume decides this.** The data skew threshold is about 10,000 children per parent, and you expect over 100,000 on some Accounts.
- **Parent locking:** loading or syncing invoices for one Account in parallel batches gives `UNABLE_TO_LOCK_ROW`. Master-detail makes this worse, because every child write also locks the parent for roll-up and sharing.
- **Sharing recalculation:** with master-detail, changing an Account's owner or sharing forces recalculation across 100,000+ children. That can run long and block other changes.
- **Roll-up cost:** a native roll-up on an Account with 100,000+ children makes every invoice save recalculate the parent.
- **Cascade delete:** deleting an Account would silently delete all of its invoices. For financial records, a lookup with delete restricted (`deleteConstraint = Restrict`) is usually safer. Confirm that with finance or compliance.

**What master-detail would give you, and why I rejected it:** native roll-ups, inherited sharing, and no separate invoice owner. Roll-ups can be replaced, and the other two don't outweigh the skew risk at this volume.

## 4. Design details for the lookup
- **Roll-ups, if needed:** compute them asynchronously. Use a scheduled batch, or Queueable or Platform Event aggregation grouped by Account (one `AggregateResult` query and one Account update per Account). Don't use an after-save flow that updates the Account on every invoice. Use a declarative roll-up tool only if it works asynchronously.
- **Sharing:** if Account is Private, set Invoice's OWD to Private. Avoid sharing rules based on Account fields. With 2M records, criteria-based sharing is expensive to recalculate.
- **Ownership skew:** don't assign all 2M invoices to one integration user. The limit is about 10,000 records per owner.
  - If one integration owner can't be avoided, give that user no role, or a role at the top of its own hierarchy branch, outside the groups used for sharing rules.
  - Don't change that user's owner or role afterwards, because it triggers sharing recalculation.
- **Loading:** sort and group invoices by Account Id in each batch. Use serial mode, or small batches, for Accounts with very large invoice counts.
- **Indexing:** filter reports and SOQL on indexed fields. The lookup is indexed, and an External Id on the invoice number helps upserts.
- **Large data volumes:** plan for selective queries and skinny tables. Consider archiving closed invoices, for example to Big Objects or an external store, if 2M keeps growing.

## 5. Test cases for `uat`
- Bulk-load 200 invoices spread over 50 Accounts, and confirm it works without lock errors.
- Load 10,000+ invoices into one Account in parallel and check for `UNABLE_TO_LOCK_ROW`, then repeat grouped by Account.
- Change the owner of a high-volume Account and time the sharing recalculation.
- Try to delete an Account that has invoices, and confirm it's blocked or cascades as intended.
- If roll-ups are needed, test the scheduled recalculation against a known invoice total.
