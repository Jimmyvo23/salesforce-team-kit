# S5: Lookup or master-detail (with-skill)

## Recommendation: Lookup (provisional until the inventory below is back)

### 1. Goal and assumptions
- `Invoice__c` has Account as its parent, with about 2M invoices and some accounts above 100,000.
- I'm assuming invoices are loaded in bulk or by an integration, and that someone will want totals such as open amount or invoice count on Account. Please correct me if either is wrong.
- Metadata targets API 62.0 (`sourceApiVersion`) and the sandbox alias `uat`. Production is deployed by a person with a change set.

**What would change the answer:**
- An existing Account trigger means any new Account logic goes in its handler, not a second trigger.
- Active Account flows or validation rules that fire on update are a concern, because the async roll-up writes to Account and runs them.
- Account owner-based sharing rules or territory assignment make skew more costly.

None of these would push me to master-detail. They only change how the roll-up is built.

### 3. Why lookup, and why not master-detail

| Point | Master-detail | Lookup |
|---|---|---|
| Sharing | Invoices inherit Account sharing | Own sharing, can be set separately |
| Ownership | No owner | Has an owner |
| Cascade delete | Always | Optional |
| Roll-ups | Native roll-up summary | None natively |

The volume decides it. Accounts with more than 100,000 invoices are well past the roughly 10,000-children-per-parent skew threshold, and that causes three problems:
- **Row locking.** Every insert or update of invoices under one Account locks that Account row for the whole transaction. Parallel loads and integrations then fail with `UNABLE_TO_LOCK_ROW`. Master-detail makes this worse because it also locks the parent for roll-up recalculation and sharing.
- **Sharing recalculation.** Changing an Account's owner or sharing recalculates access for every master-detail child, which is minutes or more for 100,000+ records. Lookup invoices hold their own sharing.
- **Roll-up cost.** Native roll-ups on a 100,000-child parent recalculate on every child save and add to the locking.

I'm rejecting master-detail for those reasons. Its benefits don't outweigh them here: automatic sharing inheritance, and native roll-ups that stop being cheap at this size.

Consequences of choosing lookup:
- Set the lookup's delete behaviour deliberately. Use **Don't allow deletion** if invoices are financial records, rather than the default clear-the-field. Deleting an Account that has over 100,000 children is also its own problem.
- Roll-ups must be built separately: an async job (Queueable or scheduled batch, grouped by Account) or a tool such as DLRS. Don't compute them in the invoice save transaction.
- Add a required field validation if an invoice must always have an Account. A lookup is nullable by default.

### 4. Loading and design details
- **Loads:** sort or group by AccountId and use serial processing where possible, so the same Account isn't locked from parallel batches.
- **Sharing:** if invoices should follow Account visibility, use Account-based sharing rules or Apex sharing, with the Account owner not routinely changing for the big accounts.
- **Owner:** assign an integration user as owner of the invoices, so ownership isn't spread over many users.
- **Indexing:** `Account__c` is indexed automatically as a lookup. For filters at this size, use selective filters (date, status, an external Id) and consider an external Id for upserts.
- **Reporting and queries:** use selective filters and avoid unfiltered queries on `Invoice__c` over 2M rows. Consider Big Objects or archiving if the volume keeps growing.

### 5. Failure handling and limits
For the async roll-up: record failures in a status or error field, retry a capped number of times, and run a scheduled sweep for Accounts that are out of date. The Account update in that job runs Account's flows, triggers and validation rules, which is what the inventory checks.

- Delete an Account with invoices and confirm the delete behaviour you chose.
