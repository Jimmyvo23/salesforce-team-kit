# Design: set `Account.Customer_Since__c` when an Opportunity is Closed Won

Target org: sandbox `uat` (from `.team/team.json`), API version 62.0 (from `sfdx-project.json`).

The recommendation is **provisional until the inventory in section 2 is back.** I have read-only tools and no shell, so I couldn't query `uat`. The repo has no `triggers/` or `flows/` folder, but the repo is not the org. It contains only `OpportunityService.cls`, which is a query helper, and the field `Opportunity.Partner_Discount__c`.

## 1. Goal and assumptions

- **Goal:** when an Opportunity becomes Closed Won, set the parent Account's `Customer_Since__c` to today, but only if it is blank.
- **Assumptions to confirm:**
  - `Customer_Since__c` is a Date field. It isn't in the repo, so please confirm that and its existence in `uat`.
  - "Today" is the running user's current date, i.e. `TODAY()` in Flow or `Date.today()` in Apex. If you'd rather use the Opportunity's `CloseDate`, say so. That would differ for backdated deals.
  - Opportunities with no Account are skipped.
  - Reopening or losing a deal later does **not** clear the field.
  - Existing Closed Won history is not backfilled. A one-off data load would handle that if you want it.

**What would change the recommendation:**
- **An active Opportunity Apex trigger exists.** The logic goes in its handler as an after-update/after-insert step. I would not add a flow, because a second entry point has no guaranteed order.
- **An Account trigger or flow also writes `Customer_Since__c`.** We need to settle which one owns the field.
- **An Account validation rule fails on the update.** The Account write would fail and roll back the Opportunity save. Either the rule needs an exception, or the update needs separate error handling.
- **An existing Opportunity after-save flow.** I'd consider extending it, or give the new flow an explicit `TriggerOrder` after it.
- **Process Builder or workflow rules on either object.** These are migration candidates. I won't add to them.

## 3. Recommendation

**An after-save record-triggered flow on Opportunity** that updates the parent Account.

**Why after-save:** the change writes to a different record (Account). A before-save flow can only change `$Record`, with no actions and no updates to other records. So before-save can't do this.

**Why a flow and not Apex:** the logic is one condition and one guarded update. Apex would add a trigger, handler and tests for no gain. It is also the right choice only if the inventory shows no existing Opportunity trigger.

**Rejected:**
- **Before-save flow:** can't write to Account, as above.
- **Formula field on Account:** it can't remember a date. A formula would also need a roll-up of Opportunities, and there is none natively because Opportunity is a lookup child of Account.
- **Apex trigger:** adds code for no gain. It becomes the answer only if the inventory shows an existing trigger.
- **Workflow Rule or Process Builder:** retired, so not used.

**Run context:** the flow runs in system context without sharing. It will update the Account even if the user closing the deal can't edit it. That seems intended here, but please confirm.

## 4. Entry criteria, logic, bulk, order of execution

**Entry (Opportunity):**
- Trigger: record created or updated. Include create so deals inserted already as Closed Won are covered.
- Condition: `IsWon = true` and `AccountId` is not null.
- Run only when the record is updated to meet the condition requirements. That means it fires on the transition, not on every later save of a won deal.
- I'd use `IsWon` rather than `StageName = 'Closed Won'`. It is stable if the stage is renamed.

**Logic:**
1. Update Records on Account, using the Opportunity's `AccountId` as the target.
2. Filter: `Id = {!$Record.AccountId}` and `Customer_Since__c` is null.
3. Set: `Customer_Since__c = {!$Flow.CurrentDate}`.

The "is null" filter makes the write idempotent, so a repeat firing or a second won deal changes nothing.

**Bulk:** 200 Opportunities on 50 Accounts closing at once is handled by one set-based Update Records element on the matching Accounts. There are no loops, and no SOQL or DML per record. Many deals on the same Account are fine, because the first write fills the field and the filter excludes the rest.

**Order of execution:** the Opportunity is saved, then any Opportunity after triggers run, then the flow runs, then roll-ups, then commit. The Account update goes through the Account's own full save order. That includes its before-save flows, triggers, validation rules and after-save flows. This is why Account is in the inventory.

**Recursion:** the flow writes only to Account, and its entry condition is on Opportunity, so it can't loop on itself. A loop could only come from an Account automation that updates Opportunities. The inventory will show whether one exists.

**TriggerOrder:** set it explicitly once the inventory shows the existing after-save flows on Opportunity.

## 5. Failure handling and limits

- **A failed Account update** (validation rule, lock, required field) fails the whole transaction, so the deal wouldn't close. If you'd prefer the deal to always close, move the update to the flow's Run Asynchronously path, and add a fault path that logs the error. Please tell me which behaviour you want. My default is synchronous, so failures are visible rather than silent.
- **Row locks:** many deals on one Account closing in parallel can contend on the Account lock. This matters only for accounts with very high Opportunity volume. I'd check for skew (an Account with more than about 10,000 Opportunities) during testing.
- **No callouts**, so the integration limits don't apply.
- **Limits:** one DML statement and one query per transaction from this flow. It is well within governor limits.

## 6. Test cases for `uat`

1. **Single deal:** an Opportunity moves to Closed Won on an Account with a blank field. The field becomes today's date.
2. **Already set:** the Account already has a date. After close, the date is unchanged.
3. **Condition not newly met:** edit a deal that is already Closed Won, or move Open to Open. The flow doesn't fire and the field is unchanged.
4. **Created as Closed Won:** the insert sets the field.
5. **Closed Lost:** the field stays blank.
6. **No Account:** the Opportunity has a null `AccountId`. It saves without error.
7. **Bulk:** 200 Opportunities across 50 Accounts, some with the field already set. Each blank Account gets today's date, the others are untouched, and there are no limit errors.
8. **Multiple won deals on one Account in one batch:** the field is set once, with no error.
9. **Reopen then re-win:** the date set the first time is kept.
10. **Permissions:** close a deal as a user with no Account edit rights. The field still updates, because of system context.
11. **Validation rule on Account** (if any exist): confirm the failure behaviour matches what you chose in section 5.
