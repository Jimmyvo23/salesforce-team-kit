**What would change the recommendation:**
- An active Opportunity or Account Apex trigger: the logic goes into that trigger's handler, not a new flow. A second trigger has no guaranteed order.
- Existing active Opportunity after-save flows: the new flow gets an explicit `TriggerOrder` after them.
- An existing flow or trigger already writing `Customer_Since__c`: extend it, don't duplicate.
- A Process Builder process or workflow rule on either object: don't add to it. Flag it as a migration candidate.
- An Account validation rule that fails on partial data: this can block the Opportunity save. It needs an exception or a different design.

## 3. Recommendation

**One after-save record-triggered flow on Opportunity** (create and update) that updates the parent Account.

- **Why after-save:** the change writes to a different record (Account). A before-save flow can only change `$Record`, so it can't do this. An after-save flow is the declarative option.
- **Why not Apex:** the logic is a single conditional parent update with no savepoints, partial success or heavy computation. Apex would add a trigger, a handler and tests for no gain. Apex becomes the choice only if the inventory shows an existing trigger on Opportunity.
- **Why not a formula field:** it needs a stored, one-time date. A formula would recompute and can't "remember" the first win.
- **Rejected:** Workflow Rule and Process Builder are retired. A roll-up of MIN(CloseDate) isn't possible, since Opportunity is a lookup child of Account. It would also give the CloseDate rather than the date of the win.

## 4. Entry criteria, logic, bulk, order of execution

**Entry condition:** run "only when a record is updated to meet the condition requirements" with `IsWon = true` and `AccountId` not null. On create, the same condition applies. Closed Won must be newly met, so later edits to a won deal don't re-run the flow.

**Logic:**
1. Take the triggering Opportunity's `AccountId`.
2. Get Records: the Account where `Id = AccountId` and `Customer_Since__c` is null. This is the idempotency check.
3. If found, Update Records: set `Customer_Since__c = $Flow.CurrentDate`.

**Bulk:** the flow interviews run in bulk, and Get Records and Update Records are collapsed across the batch. 200 Opportunities on 50 Accounts means one query and one update, with no loops or DML in loops. Several Opportunities on the same Account in one batch are safe: the update is idempotent and the value is the same day.

**Order of execution:** Opportunity before-save flows, then before triggers, then validation, then after triggers, then **this after-save flow**, then roll-ups and commit. Updating Account runs Account's own flows, triggers and validation rules in a nested save. The inventory above decides whether anything there conflicts.

**Recursion:** nothing loops. The flow writes only to Account and doesn't touch Opportunity. Once the field is set, the "is blank" check stops further writes. If an Account flow updates Opportunities, that needs a look.

**TriggerOrder:** set explicitly to fit the existing Opportunity after-save flows once the inventory is back.

## 5. Failure handling and limits

- No callouts, so none of the integration rules apply.
- Add a Fault path on Update Records. It should send an email or write to a log record without blocking the Opportunity close. If the business wants the close blocked, the fault is left unhandled instead. **Confirm which.**
- Running user needs edit access to `Customer_Since__c` on Account. After-save flows run in user context by default, so a user without Account edit access would fail. If that's likely, set the flow to run in system context without sharing, and document it.
- Limits: one SOQL query and one DML per batch for this flow. This is negligible against the 100 SOQL / 150 DML per transaction.

## 6. Tests in `uat`

1. **Bulk:** 200 Opportunities across 50 Accounts, all moved to Closed Won in one update. Expect all 50 Accounts set to today, with no limit errors.
2. **Already set:** the Account has `Customer_Since__c` filled. Close an Opportunity. Expect the date unchanged.
3. **Condition not newly met:** edit a field on an already-Closed Won Opportunity. Expect no Account update. Also move a deal to Closed Lost, and to an open stage: no change.
4. **Create as Closed Won:** a new Opportunity inserted won. Expect the date set.
5. **No Account:** a Closed Won Opportunity with a blank `AccountId`. Expect no error.
6. **Validation:** an Account with a failing validation rule. Confirm the behavior matches what you chose in section 5.
7. **Two won deals on one Account:** the date is the first one's day.
