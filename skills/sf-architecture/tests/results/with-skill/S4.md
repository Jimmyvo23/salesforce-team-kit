## 3. Recommendation (provisional)
A formula field is the right tool for a pure calculation used for display or reporting. But this one has a real risk.

- **Compile size.** The limit is 15,000 bytes compiled. Please confirm that against the current "Formula Field Limits and Restrictions" page, since older docs say 5,000. The compiled size of a formula includes the compiled size of every formula field it references. Fifteen formula inputs means fifteen compiled sizes stacked up, so this will probably hit the limit.
- **Helper formulas don't help.** Splitting the logic into intermediate formulas only helps with the 3,900-character limit. It doesn't reduce compile size.

**Decision rule:**
- **Total compiled size of the 15 inputs plus the new logic is comfortably under 15,000 bytes.** Build `Health_Score__c` as a Number formula field, with `BLANKVALUE` or `NULLVALUE` around each input so blanks don't break it.
- **It's near or over the limit, or you need to filter or index the score.** Make `Health_Score__c` a stored Number field. Calculate it in a before-save record-triggered flow on Account.
  - A before-save flow only sets fields on `$Record`, so it needs no extra DML.
  - It would use Account's existing flow order (set an explicit `TriggerOrder`) or its existing trigger handler.
  - If the inputs live on other records, use Apex or a batch job instead.

**Rejected:**
- An after-save flow, because it re-runs the save order for no gain.
- A second Apex trigger, because trigger order isn't guaranteed.
- Workflow Rules and Process Builder, because both are retired.

**What would change this:**
- An existing Account trigger means the logic goes in its handler.
- An existing before-save flow means the new one gets an explicit `TriggerOrder` that fits the existing ones.
