# S2: Same-record field (baseline)

**Recommendation: a before-save record-triggered Flow.**

This is a same-record field update with simple date math. That is what before-save flows are for. They're the fastest option because they need no extra DML. They're admin-maintainable and need no test class. The repo has no triggers, no trigger framework and no flows, so Apex would mean introducing that scaffolding for one line of logic.

**Setup**
- Object: Opportunity
- Trigger: A record is created or updated
- Entry condition: `CloseDate` is not null. Also use "Only when a record is updated to meet the condition requirements", or `ISNEW() || ISCHANGED({!$Record.CloseDate})`, so you only recalculate when CloseDate changes.
- Optimize for: Fast Field Updates (before-save)
- Action: Update `$Record.Next_Step_Date__c` = `{!$Record.CloseDate} - 7`. Date minus a number subtracts days, so no formula function is needed.

**Decisions for you**
- **Overwriting user edits:** If you only recalculate when CloseDate changes, reps can still manually adjust Next Step Date in between. If it should always be CloseDate − 7, drop the change condition. Better yet, make it a **formula field** (see below).
- **Formula field alternative:** If the value is never meant to be edited, a formula field `CloseDate - 7` is simpler still. It needs no automation and is always correct, including for existing records. The catch is that you can't edit it, and it isn't a stored value for some reporting and automation uses. I'd pick this over the Flow if "set on save" is only a means to "always equals CloseDate − 7".
- **Field:** `Next_Step_Date__c` isn't in the repo yet. It needs to be a Date field, and a formula field would need type Date as well.
- **Weekends:** CloseDate − 7 can land on a weekend. If that matters, say so, because it changes the logic.
- **Existing records:** Neither the Flow nor the trigger backfills them. Use a one-time data load or anonymous Apex for that.

**When to use Apex instead:** if you already plan Opportunity triggers with other logic, or need complex bulk or cross-object behavior. In that case, use a before-insert/update trigger that delegates to a handler. It would go in `OpportunityService` or a new handler class, and loop over `Trigger.new` to set the field. That also needs a test class.
