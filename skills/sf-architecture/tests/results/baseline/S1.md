# Design: stamp `Account.Customer_Since__c` on Closed Won

## What the repo shows
- `Customer_Since__c` isn't in source. It may exist only in the org, or it may not exist yet. I haven't queried `uat`. Step 0 below covers this.
- There are no triggers or flows on Opportunity. The only Opportunity code is `OpportunityService.cls`, a `with sharing` service class with one read method.
- Production deploys go through change sets, which you do by hand. Everything below is scoped to `uat` and should be packaged cleanly for a change set.

## Recommendation: record-triggered Flow (after save)
Use a Flow rather than Apex. The rule is one condition and one field update, and an admin can maintain it. Apex would only be worth it if you later need complex logic or bulk volumes beyond what Flow handles.

**Trigger**
- Object: Opportunity
- Runs on create or update, after save
- Entry condition: `IsWon = true` and `AccountId` is not null
- Run only when the record is created or updated to meet the condition. This fires only on the transition into Won, not on every later edit.

**Logic**
1. Get Records: the Account by `{!$Record.AccountId}`, returning only `Id` and `Customer_Since__c`.
2. Decision: `Customer_Since__c` is null. If not, end.
3. Update Records: set `Customer_Since__c = {!$Flow.CurrentDate}` on that Account.

I'd use `IsWon` rather than `StageName = 'Closed Won'`. It survives stage renames and works if there are several won stages.

**Alternative that avoids the Get Records element:** put the blank check in the Update Records filter (`Id = AccountId` and `Customer_Since__c` is null). That makes one fewer element and it's naturally idempotent. I'd use this version.

## Design decisions to confirm
| Question | My default |
|---|---|
| **"Today"** | `$Flow.CurrentDate` uses the running user's time zone. Use that unless the business wants the Close Date instead. For back-dated deals, `CloseDate` may be more accurate. You said today, so I'm going with today. |
| **Field type** | Must be Date. If it's DateTime, the formula changes to `NOW()`. |
| **Run context** | Run in system context so users without Account edit rights can still close deals. Check that this is acceptable. |
| **Reopen / Closed Lost later** | Don't clear the field. It only ever gets set once. |
| **Multiple wins in one transaction** | Flow bulkifies this. Two Opportunities on the same Account in one batch both try to set the date, and the result is harmless because both write the same value. |
| **Existing customers** | The Flow only affects future wins. Backfill separately if needed. A one-off script could set `Customer_Since__c` to the earliest won `CloseDate` per Account. I'd treat that as its own task and run it only after you approve. |

## Build and test plan in `uat`
0. **Check the field.** Confirm `Customer_Since__c` exists on Account with type Date. If not, create it (Date, not required, with field-level security and page layout placement). Retrieve it into source so the repo matches the org.
1. **Build the Flow** as described above. Save it as a draft, then activate it in `uat` once the tests below pass.
2. **Test cases:**
   - Win an Opportunity on an Account with a blank field. The field is set to today.
   - Win a second Opportunity on the same Account. The date is unchanged.
   - Win an Opportunity on an Account with a pre-filled date. The date is unchanged.
   - Edit an already-Won Opportunity. Nothing fires.
   - Move an Opportunity to Closed Lost. Nothing happens.
   - Bulk: update about 200 Opportunities across about 50 Accounts, and confirm there are no governor-limit errors.
   - Run as a user with minimal Account permissions, to confirm the system-context behavior.
3. **Check for conflicts.** Look in `uat` for existing Account or Opportunity automation that touches this field or runs on the same event: validation rules, other flows, managed packages.
4. **Package for production.** Put the field, the Flow, and any field-level security changes in one outbound change set. Deploy it yourself.
