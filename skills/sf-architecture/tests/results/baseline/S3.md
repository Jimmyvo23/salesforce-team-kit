# S3: ERP integration (baseline)

This is a Salesforce (SFDX) project. It has no Order code and no existing integration code, only a small `OpportunityService` class, so this would be the first callout. My recommendation is to send the order asynchronously, using a trigger, a Queueable and a Named Credential.

## Recommended architecture

**1. Trigger on Order, handler class, no logic in the trigger**
- An `after update` trigger on `Order` detects the transition to `Status = 'Activated'`. Compare `Trigger.new` with `Trigger.oldMap`, so edits to orders that are already activated don't re-send.
- The trigger delegates to a handler/service class, following the `OpportunityService` pattern, for example `OrderActivationService`.
- If you prefer declarative, a Record-Triggered Flow can do the same detection and call an Invocable Apex action. Either way, the callout itself belongs in Apex.

**2. Asynchronous callout with `Queueable` and `Database.AllowsCallouts`**
- Apex can't make a callout from inside a trigger transaction. The callout would also hold up the user's save and tie it to ERP availability.
- The Queueable takes Order IDs, re-queries the data it needs (using `WITH USER_MODE` or system mode, whichever you decide is right), and POSTs it.
- Batch the IDs so bulk activations don't hit the limit of 100 callouts per transaction.

**3. Named Credential and External Credential for `https://erp.example.com`**
- Don't hardcode the URL or secrets in Apex. Use `callout:ERP_Orders/api/orders`.
- This keeps auth out of code and lets sandbox (`uat`) point at an ERP test endpoint while production points at the real one, with no code change between orgs.

**4. Idempotency**
- Send a stable idempotency key, such as the Order ID or an external ID, so a retry can't create a duplicate order in the ERP. This needs ERP support, so check whether the API accepts one.

**5. Status tracking and retry**
- Add fields on Order such as `ERP_Sync_Status__c` (Pending, Sent, Failed), `ERP_Order_Id__c`, `ERP_Last_Error__c` and `ERP_Last_Attempt__c`.
- On a 2xx response, store the ERP ID and mark the order Sent. On a 5xx or timeout, re-enqueue with a capped retry count. A 4xx is a data problem, so mark it Failed and don't retry.
- A scheduled job can sweep Failed or stuck-Pending orders. Surface failures in a list view, report or alert so they don't go unnoticed.

**6. Layering for testability**
- Keep the layers separate: trigger, then `OrderActivationService` (decides what to send), then `ErpOrderQueueable` (async wrapper), then `ErpClient` (HTTP, payload serialization and response parsing).
- Tests use `HttpCalloutMock`, so no real ERP is needed.

## Alternative to consider
If the ERP is flaky, order volume is high, or other systems also need order events, use **Platform Events** (or Change Data Capture) with a subscriber that makes the callout. This decouples Salesforce from the ERP and gives you replay, but it adds moving parts. For a single ERP consumer, the Queueable approach is simpler and I'd start there.

## Questions that would change the design
- Does the ERP API support idempotency keys, and what does it return on duplicates?
- What is the expected volume, and are bulk activations (data loads, mass updates) common?
- Does the ERP need to send a result back asynchronously, such as an invoice or fulfillment status? If so, you'll also need an inbound REST endpoint or a webhook receiver.
- What is the auth method (OAuth client credentials, API key, mutual TLS)? That determines the External Credential setup.
