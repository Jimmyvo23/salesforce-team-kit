# Flow: Copy Account billing address to Contacts' mailing address

I haven't built any metadata. There are no flow files in the repo, so this is the design only. The design is provisional until the inventory results in section 1 are back.

## 1. What already runs on Account and Contact (check first)

Run these against the sandbox alias (`<sandbox-alias>`, not production). Run each query for both **Account** and **Contact**, since the flow triggers on one and writes to the other. Or open **Setup > Flow Trigger Explorer** for each object.

```sh
sf data query -o <sandbox-alias> -q "SELECT ApiName, Label, ProcessType, TriggerType, RecordTriggerType, TriggerOrder, IsActive FROM FlowDefinitionView WHERE TriggerObjectOrEventLabel = 'Account' ORDER BY TriggerType, TriggerOrder"

sf data query --use-tooling-api -o <sandbox-alias> -q "SELECT Name, Status, UsageBeforeUpdate, UsageAfterUpdate FROM ApexTrigger WHERE TableEnumOrId = 'Account'"
sf data query --use-tooling-api -o <sandbox-alias> -q "SELECT Id, Name FROM WorkflowRule WHERE TableEnumOrId = 'Account'"
sf data query --use-tooling-api -o <sandbox-alias> -q "SELECT ValidationName, Active, ErrorMessage FROM ValidationRule WHERE EntityDefinition.QualifiedApiName = 'Contact'"
```

Repeat the same five with `'Contact'` in place of `'Account'`.

What would change the design:
- **An existing Account after-save flow that already syncs address or does related work:** add a path to it, or give this flow an explicit Trigger Order. Don't add a second, overlapping flow.
- **A Contact trigger or flow that writes `Mailing*` fields:** the two would overwrite each other. Put the logic in one place.
- **An active Process Builder process or Workflow Rule doing the same job:** plan its migration. Otherwise the copy happens twice.
- **Contact validation rules on `Mailing*` fields:** they can block this flow's update, so the fault path matters.

## 2. How versions work

- Saving an active flow in Flow Builder means **Save As New Version**, and the new version is inactive.
- Only one version is active. Activating a new one deactivates the previous one.
- Running or paused interviews finish on the version they started on.
- The old version stays for rollback. Don't delete it.

## 3. Flow type and why

**Record-triggered, after-save (Actions and Related Records)** on Account. The flow changes *other* records (Contacts), and a before-save flow can't do that.

- **Name:** `Account_AfterSave_SyncBillingToContactMailing`
- **apiVersion:** `62.0`, from `sourceApiVersion` in `sfdx-project.json`
- **Description:** "When an Account's billing address changes, copies it to the Mailing address of its Contacts."

## 4. Element by element

**1. Start**
- **Object and trigger:** Account, **A record is updated**.
- **Entry condition:** *Formula evaluates to true*:
  ```
  OR(
    ISCHANGED({!$Record.BillingStreet}),
    ISCHANGED({!$Record.BillingCity}),
    ISCHANGED({!$Record.BillingState}),
    ISCHANGED({!$Record.BillingPostalCode}),
    ISCHANGED({!$Record.BillingCountry})
  )
  ```
  - It fires only when the address changes, not on every Account save.
  - `ISCHANGED` is never true on create, and a new Account has no Contacts yet, so "updated" is enough.
  - If State and Country picklists are enabled, the formula and the update must use `BillingStateCode` / `BillingCountryCode` and `MailingStateCode` / `MailingCountryCode`. Confirm this in the org.
- **Optimize for:** Actions and Related Records.

**2. Update Records `Update Contact Mailing Address`**
- **How to find records:** Specify conditions. Object: Contact. Condition: `AccountId` Equals `{!$Record.Id}`.
- **Field values:**

  | Contact field | Value |
  |---|---|
  | `MailingStreet` | `{!$Record.BillingStreet}` |
  | `MailingCity` | `{!$Record.BillingCity}` |
  | `MailingState` | `{!$Record.BillingState}` |
  | `MailingPostalCode` | `{!$Record.BillingPostalCode}` |
  | `MailingCountry` | `{!$Record.BillingCountry}` |

- **Connectors:** the normal connector goes to the end. The **fault connector** goes to element 3.
- **No Loop.** One Update Records with criteria handles every Contact, so there is nothing in a loop.
- A blank billing field blanks the Mailing field. That keeps the addresses identical, which I assume is the intent.

**3. Fault handling (log and continue)**
- **Send Email `Email Admin – Contact Address Sync Failed`** goes to an admin address, which should be a custom metadata value, not hard-coded. The body includes:
  - `{!$Flow.FaultMessage}`
  - `{!$Record.Id}`
  - The element name, "Update Contact Mailing Address"
- The email element needs its **own fault connector**, which goes to the end. Without one, a failed email would fail the whole flow and the Account save.
- The Account save still succeeds, and only the Contact update is lost. If you'd rather block the Account save, end the fault path in a **Custom Error** element. That rolls back everything, including emails, so log with a Publish Immediately platform event instead.

## 5. Bulk behaviour

A list edit or data load saves up to **200 Accounts** per transaction, and each runs its own interview. Salesforce batches interviews waiting at the same element, so there is no per-record query or DML.

The limits are still shared across the whole transaction: 100 SOQL queries, 150 DML statements and **10,000 DML rows**. 200 Accounts with 60 Contacts each is 12,000 Contact rows, which fails. A governor-limit error rolls back the whole transaction even with a fault connector.

**Assumption:** most Accounts have fewer than about 50 Contacts and bulk address edits are rare. If that's wrong, move element 2 to an **asynchronous path** or Batch Apex.

The Contact update also runs Contact flows, triggers and validation rules.

## 6. Run context and access

- **Run context:** record-triggered flows run in **system context without sharing**. The editing user's permissions don't limit the Contact update, so users who can edit an Account can indirectly change Contacts they couldn't edit.
- **Permissions:** no extra permissions are needed, because there is no screen and no Apex.

## 7. Testing, activation and rollback (sandbox only)

**Tests come first.** All work happens in `<sandbox-alias>`.

1. **Flow tests** (Flow Builder > View Tests), with assertions:
   - **Billing street changes:** Contacts get the new Mailing address.
   - **A non-address field changes:** the flow doesn't fire and Contacts are untouched.
   - **Account with no Contacts:** no error.
   - **Billing address cleared:** Mailing fields are blanked.
2. **Debug** in rollback mode, then test with real records.
3. **Real records:** edit a few Accounts. Then do a list edit or load of 200 Accounts with a realistic Contact count, and check the DML row total.
4. **Fault path:** force a Contact validation failure and confirm the admin email arrives and the Account still saves.
5. **Deploy status:** before any deploy, check the flow file's `<status>`. `Active` activates it on deploy, before you've tested it. Deploy as `Draft`, test, then activate.
6. **Record the version number:** write down the current active version before activating.
7. **Activate the new version** in the sandbox only after the tests pass. Setup > Flows > the flow > View Details and Versions > Activate.
8. **Roll back** by re-activating the previous version. Then check which Contacts the bad version already changed.
9. **Production:** a person moves the flow to production with a change set and decides about activation there.
