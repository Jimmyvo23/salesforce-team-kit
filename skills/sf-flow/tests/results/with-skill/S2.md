Nothing exists in the repo yet (no `.flow-meta.xml` files), so this is a new flow. `sourceApiVersion` is **62.0**, so the flow gets `apiVersion` 62.0. I haven't run any org queries, so the design is provisional until the inventory below is back.

## 1. Existing automation (check first)

Run these against the sandbox alias (I've written `<sandbox-alias>`, so substitute yours), once for `Account` and once for `Contact`. The flow triggers on Account and writes to Contact. Or open **Setup > Flow Trigger Explorer** for both objects.

```sh

sf data query --use-tooling-api -o <sandbox-alias> -q "SELECT Id, MasterLabel, Status FROM Flow WHERE ProcessType = 'Workflow' AND Status = 'Active'"
sf data query --use-tooling-api -o <sandbox-alias> -q "SELECT Name, Status, UsageAfterUpdate FROM ApexTrigger WHERE TableEnumOrId IN ('Account','Contact')"
sf data query --use-tooling-api -o <sandbox-alias> -q "SELECT Id, Name FROM WorkflowRule WHERE TableEnumOrId IN ('Account','Contact')"
sf data query --use-tooling-api -o <sandbox-alias> -q "SELECT ValidationName, Active, ErrorMessage FROM ValidationRule WHERE EntityDefinition.QualifiedApiName = 'Contact'"
```

What would change the design:
- **An existing Account after-save flow that already syncs addresses:** add a Decision outcome or path to it, or set an explicit Trigger Order, rather than creating a second flow.
- **An active Process Builder process or Workflow Rule doing the same job:** migrate it. Otherwise the update happens twice.
- **A Contact trigger or flow that reacts to address changes:** it will fire for every Contact this flow updates. That matters for the bulk limits.
- **Contact validation rules that require fields:** they can reject the update. This is why the fault path matters.

## 2. Flow type

**Record-triggered, after-save, on Account.** The flow changes other records (Contacts), which a before-save flow can't do. A before-save flow can only set fields on the triggering record.

## 3. Design

**Name:** `Account_AfterSave_SyncBillingToContactMailing`. Add a description to the flow and to each element.

1. **Start** (Account)
   - Trigger: **A record is updated**, Actions and Related Records.
   - Condition requirements: **Formula evaluates to true**.
     ```
     OR(
       ISCHANGED({!$Record.BillingStreet}),
       ISCHANGED({!$Record.BillingCity}),
       ISCHANGED({!$Record.BillingState}),
       ISCHANGED({!$Record.BillingPostalCode}),
       ISCHANGED({!$Record.BillingCountry})
     )
     ```
   - Because it is an `ISCHANGED` formula, it fires only when an address field actually changes, not on every Account edit.
   - A new Account has no Contacts yet, so "updated" is enough. If your org uses state and country picklists, use `BillingStateCode` and `BillingCountryCode` instead or as well.

2. **Update Records `Update Contact Mailing Address`**
   - Choose "Specify conditions to identify records, and set fields individually". There is no Loop and no Get Records.
   - Object: Contact. Filter: `AccountId` Equals `{!$Record.Id}`.
   - Field values:

     | Contact field | Value |
     |---|---|
     | `MailingStreet` | `{!$Record.BillingStreet}` |
     | `MailingCity` | `{!$Record.BillingCity}` |
     | `MailingState` | `{!$Record.BillingState}` |
     | `MailingPostalCode` | `{!$Record.BillingPostalCode}` |
     | `MailingCountry` | `{!$Record.BillingCountry}` |

   - **Fault connector** goes to element 3.
   - Assumption: this overwrites the Mailing address on all the Account's Contacts. To keep Contacts that deliberately have a different address, add filters that match the old address, for example `MailingStreet` Equals `{!$Record__Prior.BillingStreet}`. Tell me if you want that.

3. **Send Email `Email Admin Contact Sync Failure`** (log and continue)
   - Recipient: an admin address held in custom metadata or a custom label, not typed into the flow.
   - Body: `{!$Flow.FaultMessage}`, `{!$Record.Id}` and the element name "Update Contact Mailing Address".
   - **Its own fault connector goes to the end of the flow.** Leaving it off would make a failed email fail the whole flow and the Account save.
   - I chose log and continue because the Account billing edit is the user's real work and shouldn't be blocked by a Contact problem. The trade-off is that on a failure the Contacts stay out of sync, and only the email tells anyone. If the sync must be all-or-nothing, end in a **Custom Error** element instead. That rolls back the Account change too.

## 4. Bulk behaviour

A list edit or data load saves up to **200 Accounts per transaction**, and each runs its own interview. Salesforce batches the interviews waiting at the same element, so this is one Update Records element rather than one per Account. The transaction limits are still shared: 100 SOQL queries, 150 DML statements and **10,000 DML rows**.
- 200 Accounts with 60 Contacts each is 12,000 Contact rows, which **fails** the whole transaction.
- A governor-limit error rolls back everything, even with a fault connector.
- Contact validation rules and Contact automation run for every updated Contact.

I assumed addresses are edited one Account at a time, or in small batches, with fewer than about 50 Contacts per Account. If large loads or Accounts with thousands of Contacts are realistic, move element 2 to an **asynchronous path** or to Batch Apex. That is the first thing to confirm.

## 5. Run context and access

A record-triggered flow runs in **system context without sharing**, so the editing user's Contact permissions don't limit it. Users who can edit an Account billing address can therefore change Contacts they couldn't edit themselves. Confirm that is acceptable. Leave "How to Run the Flow" at its default.

## 6. How versions work

A flow has versions (up to 50), and only one is active. Saving changes to an active flow in Flow Builder means **Save As New Version**, and the new one is inactive until you activate it. Activating it deactivates the previous version, which stays available for rollback. Interviews already running finish on the version they started on. Deploying a flow file also creates a new version, and `<status>Active</status>` activates it on deploy. Deploy this one with `<status>Draft</status>` so it can be tested first.

## 7. Testing and activation (sandbox only)

1. **Flow tests** (Flow Builder > View Tests), with assertions:
   - A street change updates the Contacts.
   - A change to a non-address field (for example Phone) leaves the Contacts untouched.
   - An Account with no Contacts runs without error.
2. **Debug** with rollback mode on, then real records:
   - Update one Account with several Contacts.
   - Update 200 Accounts by list edit or data load, with few Contacts each, and check there are no limit errors.
   - Force a failure, for example a Contact validation rule, and confirm the admin email arrives and the Account still saves.
3. **Activate only after the tests pass.** Before activating, note the version number of any flow already doing this so you can roll back. Then activate in the sandbox (Setup > Flows > the flow > View Details and Versions > Activate). If something goes wrong, activate the previous version again and check what the bad version already changed. Keep the old versions.
4. If an old Process Builder process or Workflow Rule does this job, **deactivate it in the same step** as activating the flow so they never both run.
5. **Production:** a person moves the flow with a change set and decides about activation there.
