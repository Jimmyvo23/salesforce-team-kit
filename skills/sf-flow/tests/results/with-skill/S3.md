## 2. How versions work

Saving changes to an active flow in Flow Builder creates a new version that is inactive. Only one version is active at a time. Activating a new version deactivates the old one, but the old version stays for rollback. Interviews already running or paused finish on the version they started on.

A deployed flow file also creates a new version. Its `<status>` decides whether that version goes live straight away. I'll deploy with `<status>Draft</status>`, test, then activate.

## 3. Migration approach

1. **Try Setup > Migrate to Flow on `Opp_Stage_PB`.** It handles record-triggered processes. Review every item marked **Needs Review**.
2. **If it can't convert the process, rebuild it.** I'll write the XML into `force-app/main/default/flows/` with `apiVersion` 62.0, taken from `sourceApiVersion`. I won't hand-edit any retrieved Process Builder metadata.

Mapping, assuming a typical stage-driven process:

| Process Builder | Flow |
|---|---|
| Criteria node (`StageName` is changed to X) | Entry condition, or a Decision outcome per stage |
| Update fields on the same Opportunity | **Before-save** flow `Opportunity_BeforeSave_StageUpdates` |
| Create Task, update Account or Contact, email, Apex, post | **After-save** flow `Opportunity_AfterSave_StageActions` |
| Scheduled actions | Scheduled path on the after-save flow |
| "Only when specified changes are made" | "Only when a record is updated to meet the condition requirements" |

I'll split the work into two flows only if the process does both kinds of action. Otherwise it's one flow.

**Entry condition:** the trigger is "A record is updated" (or created and updated, if the process fired on create). The condition is the target stage, for example `StageName` Equals `<stage>`, with `doesRequireRecordChangedToMeetCriteria` = true. That way the flow runs once when the stage changes, not on every later edit. If the process watched several fields, I'll use a formula with `OR(ISCHANGED({!$Record.StageName}), …)`. I'll make the writes idempotent where I can.

**Elements:** I'll name each one by verb plus object, for example `Create Follow-Up Task`, and give each a description.

**Fault paths:** every Create, Update, Delete, Get Records, Apex or subflow, and email element gets a fault connector, including Get Records in the before-save flow. I'll pick one approach and name it:
- **Log and continue (my default):** the fault path sends an admin email with `{!$Flow.FaultMessage}`, the Opportunity Id and the element name. The email element also has a fault connector that goes to the end. The save still succeeds, and only the failed element's work is lost.
- **Block the save:** end in a Custom Error element. This rolls back everything, including any log record, so I wouldn't log with a record insert.

If the process updated related records, I'll use one Update Records element with criteria. There will be no Get, Create, Update or Delete inside a Loop.

**Bulk:** a data load or list edit saves up to 200 Opportunities per transaction. Limits are shared across everything in that transaction: 100 SOQL queries, 150 DML statements and 10,000 DML rows. If the process updates children, such as 200 Opportunities with 60 line items each, that's 12,000 rows and it fails. If so, I'll move that part to an asynchronous path or Batch Apex. A governor-limit error rolls back the whole transaction, even with a fault connector. Related updates also run the related object's own automation and validation rules.

**Run context:** record-triggered flows run in system context without sharing, so the running user's permissions don't limit them. The process behaved the same way. I won't change "How to Run the Flow". If the process called Apex, that class uses its own sharing. `OpportunityService` is `with sharing` and uses `USER_MODE`, but it isn't an invocable method.
