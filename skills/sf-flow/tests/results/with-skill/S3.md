## 2. How versions work

Saving changes to an active flow in Flow Builder creates a new, inactive version. Only one version is active at a time. Activating a new version deactivates the previous one, and running or paused interviews finish on the version they started on. The old version stays, so you can roll back by reactivating it. The same applies to deploys: a deployed flow file creates a new version, and its `<status>` decides whether it activates on deploy. I'll deploy as `Draft`, test, then activate.

## 3. Migration steps

1. **Convert.** Use **Setup > Migrate to Flow** on `Opp_Stage_PB` in `uat`.
   - It converts record-triggered processes only. It converts scheduled actions only if you migrate a single criterion.
   - Review every item marked **Needs Review**.
   - Don't hand-edit retrieved process metadata (`processType` `Workflow`).
2. **Rebuild by hand if the tool can't convert it.** The mapping is:
   - Each criteria node becomes a Decision outcome, or its own flow.
   - Updates to the same Opportunity go in a **before-save** flow.
   - Other actions (Tasks, emails, related records, Apex) go in an **after-save** flow.
   - Scheduled actions become scheduled paths.
   - "Only when specified changes are made" becomes "Only when a record is updated to meet the condition requirements".
3. **Entry condition.** I'd expect the process to key off `StageName`. For a target stage, use `StageName` Equals `<stage>` with "Only when a record is updated to meet the condition requirements". Use "created or updated" if Opportunities can be created already in that stage. For "any stage change", use `ISCHANGED({!$Record.StageName})` as a formula, and `OR(ISNEW(), ISCHANGED(...))` if create matters.
4. **Fault paths.** Every Create, Update, Get, Apex action, subflow and email element gets a fault connector.
   - For log and continue, send an admin email with `{!$Flow.FaultMessage}`, the record Id and the element name. The email element needs its own fault connector that goes to the end.
   - For block the save, use a Custom Error, and log with a Publish Immediately platform event because the rollback would discard an email.
   - I'd default to log and continue unless the process blocked saves.
5. **No loops with DML.** Use one Update Records with criteria, or build a collection in the loop and update it once after.
6. **Bulk.** A data load saves up to 200 Opportunities per transaction, and each gets its own interview. Limits are shared across the transaction: 100 SOQL queries, 150 DML statements, 10,000 DML rows. If the process touches many children per Opportunity (for example 200 × 60 line items = 12,000 rows), move that work to an asynchronous path.
7. **Run context.** Record-triggered flows run in system context without sharing, so user permissions don't limit them. The old process did the same. If an Apex action is involved, it runs under its own class's sharing. `OpportunityService` is `with sharing` and uses `WITH USER_MODE`.
8. **Naming.** `Opportunity_BeforeSave_StageUpdates` and/or `Opportunity_AfterSave_StageActions`, each with a description on the flow and every element. I'll follow your naming convention if you have one. `apiVersion` is 62.0.
