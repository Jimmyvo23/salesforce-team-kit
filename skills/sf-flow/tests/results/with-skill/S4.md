A screen flow doesn't trigger on an object. It does write whatever `logVisit` writes, probably a Visit record, an Event or Task, or both. Run these in **uat**, replacing `<VisitObject>` with the object the method writes to (`Visit__c`, `Event` or `Task`):

```sh
sf data query --use-tooling-api -o uat -q "SELECT ValidationName, Active, ErrorMessage FROM ValidationRule WHERE EntityDefinition.QualifiedApiName = '<VisitObject>'"
```

You can also open **Setup > Flow Trigger Explorer** for the object. How the results change the design:
- **A record-triggered flow, trigger or Process Builder process on the visit object that already creates a Task or sends a notification.** `logVisit` may duplicate it, so the design needs a change to one side.
- **A validation rule on the visit object.** Its message has to be readable on the error screen, or the screen flow must check the same rule up front.
- **No existing automation.** The design below stands.

## Step 2: Flow type

This is a **screen flow** because reps enter data. The record-triggered types don't fit, since nothing is saving a record to start the flow.

- **API name:** `Visit_Screen_LogSiteVisit` (follows `<Object>_<Timing>_<Purpose>`; there are no existing flows to take a convention from).
- **Label:** Log Site Visit.
- **Launch from:** a quick action on **Account** (or the site object) that passes `recordId`. That way the rep doesn't pick the site, and the flow works on mobile.

## Assumed Apex contract (confirm against the class)

```apex
public with sharing class VisitService {
    public class Request {
        @InvocableVariable(required=true) public Id siteId;          // Account/site
        @InvocableVariable(required=true) public Datetime visitDate;
        @InvocableVariable public String visitType;
        @InvocableVariable public String notes;
        @InvocableVariable public Boolean followUpRequired;
        @InvocableVariable public Date followUpDate;
    }
    public class Result {
        @InvocableVariable public Boolean isSuccess;
        @InvocableVariable public String errorMessage;
        @InvocableVariable public Id visitId;
    }
    @InvocableMethod(label='Log Visit')
    public static List<Result> logVisit(List<Request> requests) { … }
}
```

The method takes a list and must return one result per request, in the same order. If the real class takes primitives or a different shape, only the Apex action's input mapping changes. Please check whether the class says `with sharing` and uses `WITH USER_MODE`, like `OpportunityService`. That decides what the Apex action enforces (see Step 7).

## Element-by-element design

**Variables**
- `recordId` (Text, input): the site Id from the quick action.
- `varResult` (Apex-defined `VisitService.Result`, or the action's output): holds the action's output.

**1. Get Records `Get Site`**
- Object: Account (or your site object). Filter: `Id` Equals `{!recordId}`. Store the first record, with only Id and Name.
- **Fault connector** goes to element 8 (error screen).
- If no record is found, the Decision in element 2 sends the rep to the error screen.

**2. Decision `Site Found?`**
- Yes: continue to the screen. Default outcome: go to element 8.

**3. Screen `Visit Details`** (the only input screen)
- Display text: "Visit to {!Get_Site.Name}".
- **Date/Time `Visit Date`**: required, default `{!$Flow.CurrentDateTime}`, with a validation rule that it is not in the future.
- **Picklist `Visit Type`**: required. Use a global value set or a picklist field choice, not hard-coded values.
- **Long Text Area `Notes`**: optional.
- **Checkbox `Follow-up Required`**.
- **Date `Follow-up Date`**: visible only when the checkbox is true, and required then. Validation: it is after the visit date.
- Button: **Next** and **Cancel**. Cancel finishes the flow with nothing saved.

**4. Assignment `Build Visit Request`**
- Fills the Apex request variables from the screen components and `{!recordId}`.

**5. Action (Apex) `Log Visit`: `VisitService.logVisit`**
- Inputs mapped to the request variables above. Outputs stored in `varResult`.
- **Fault connector** goes to element 8 for thrown exceptions.
- It sits outside any loop. It is a single call.

**6. Decision `Visit Logged?`**
- Yes: `varResult.isSuccess` Equals `true` goes to the confirmation screen. Default outcome goes to element 8 and shows `varResult.errorMessage`.

**7. Screen `Visit Logged`** (confirmation)
- Text: "Visit saved." With a link to the new visit if the class returns `visitId`. Button: Finish.

**8. Screen `Visit Not Saved`** (error screen)
- Text: "We couldn't save the visit. Your entries are kept. Try again or contact your admin." Button: **Back**, which returns to element 3 with the entries kept.
- If `isSuccess` is false and `errorMessage` is meant for reps (validation text, for instance), show it. Never show `{!$Flow.FaultMessage}` to the rep.
- Element 8 is reached from the faults of elements 1 and 5, and from both Decisions.

**Admin notification (optional, recommended).** Put a **Send Email** action (`Notify Admin of Visit Failure`) before element 8 on the fault path of element 5. It includes `{!$Flow.FaultMessage}`, `{!recordId}`, the running user and the element name. **Its own fault connector goes to element 8 too**, so a failed email can't break the flow.

## Bulk behaviour

A screen flow runs one interview per rep action, so there is one `logVisit` call with a list of one. It isn't a 200-record case. But the method is invocable, so other flows can call it with up to 200 requests at once. It must not do SOQL or DML per request: collect Ids first, query once, and do a single insert. It must also return results in the same order and size as the input. If the class writes one row per request, 200 visits is 200 DML rows, well under the 10,000-row limit. It becomes a problem only if each visit also touches children, for example every contact on the site. Please check that the class does neither.

## Step 7: Run context and access

- The flow runs in **user context**, because a rep launches it from a quick action. The rep's object, field and record access applies to the Get Records element and to the screens.
- The Apex action runs under the class's own sharing keyword. If it is `with sharing` and uses `WITH USER_MODE`, reps need create access on the visit object and its fields. If it runs `without sharing`, it bypasses that access, so confirm that's intended.
- Create **one permission set** for reps (for example `Visit_Logger`) containing:
  - **Run Flows**;
  - the flow, if the flow's access override is on;
  - **Apex Class Access** to `VisitService`;
  - Read on the site object and Create on the visit object, with the fields.
- Don't change **How to Run the Flow**. The default is what we want.

## Versions, testing and activation

**How versions work.** Saving an active flow in Flow Builder creates a new, inactive version (**Save As New Version**). Only one version is active at a time. Activating a new one deactivates the old one, and interviews already running finish on the version they started on. The old version stays for rollback. This is a new flow, so the first version is version 1, and nothing is replaced yet.

**Deploying.** If the flow file is deployed, `<status>` decides whether it is live on deploy. Deploy with `<status>Draft</status>` to **uat**, test, then activate.

**Tests (uat). Activation waits until these pass.** Screen flows have no Flow tests, so:
1. **Debug** in Flow Builder with a real site Id: the happy path, and the follow-up checkbox on and off.
2. **Validation:** a future visit date, a follow-up date before the visit, and a missing required field.
3. **Apex failure:** make `logVisit` return `isSuccess = false` and then throw an exception. Confirm both reach the error screen, entries are kept, and no `FaultMessage` shows.
4. **Run it as a test rep** (a user with only the `Visit_Logger` permission set) from the real quick action, on desktop and mobile.
5. **Missing access:** a user without the Apex class access should see a clear failure, not a blank screen.
6. **If another flow calls `logVisit`:** run it with 200 requests and check the limits.

**Activate** in uat: Setup > Flows > Log Site Visit > View Details and Versions > Activate. Record the previous version number first. For a first version there is none, so the rollback is to deactivate the flow and remove the quick action.

**Production.** A person moves it with a change set and decides about activation there. I won't plan that.
