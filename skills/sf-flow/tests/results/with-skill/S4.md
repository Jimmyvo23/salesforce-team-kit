## 2. Flow type

This is a **screen flow**, because reps enter the data. It's launched from a Lightning record page quick action or a utility bar item. Launching it from an Account or Contact page gives it `recordId`.

## 3. Assumed Apex contract (confirm)

`@InvocableMethod` takes a `List<Request>` and must return a `List<Result>` of the same size and order.

| Direction | Name | Type |
|---|---|---|
| Input | `accountId` | Id |
| Input | `visitDate` | Date |
| Input | `visitType` | Text |
| Input | `notes` | Text |
| Input | `outcome` | Text (optional) |
| Output | `isSuccess` | Boolean |
| Output | `errorMessage` | Text |
| Output | `visitId` | Id |

If the real signature differs, only element 5 changes.

## 4. Elements

**Variables and resources**
- `recordId` (Text, input): the Account Id from the page.
- `vVisitId` (Text, output).
- `vErrorText` (Text).
- Formula `fxToday` (Date): `{!$Flow.CurrentDate}`.

**Elements**
1. **Get Records `Get Account`**
   - Object: Account. Filter: `Id` = `{!recordId}`. Store the first record only, with these fields: Id, Name.
   - Fault connector: goes to element 8, `Error Screen`.
   - Why: it shows the rep the account name and confirms they can see the record.
2. **Screen `Visit Details`**
   - Header: "Log a visit: {!Get_Account.Name}".
   - **Date** `Visit Date`: required, default `{!fxToday}`.
   - **Picklist** `Visit Type`: required. Use a global value set or a choice resource, not hard-coded text.
   - **Long Text** `Notes`.
   - **Picklist** `Outcome`.
   - Validation on Visit Date: `{!Visit_Date} <= {!fxToday}`, with the message "Visit date can't be in the future." Remove this rule if future-dated visits are allowed.
3. **Decision `Check Required Input`**
   - Only needed if some validation can't be expressed on the screen. Otherwise skip it.
4. **Assignment `Set Request Values`**
   - It sets the Apex input variables from the screen fields.
5. **Action (Apex) `Log Visit`**
   - Action: `VisitService.logVisit`. Inputs and outputs are as in section 3.
   - Fault connector: goes to element 8, `Error Screen`. This catches thrown exceptions.
   - It sits outside any loop. It's one call for one visit.
6. **Decision `Was Visit Logged`**
   - Outcome `Success`: `{!Log_Visit.isSuccess}` Equals `true`, goes to element 7.
   - Default outcome `Failed`: assign `vErrorText` = `{!Log_Visit.errorMessage}`, then go to element 8.
   - This covers Apex that returns a failure without throwing.
7. **Screen `Visit Logged`**
   - Shows "Visit logged." with a link to `{!vVisitId}`. The Finish button closes the flow.
8. **Screen `Error Screen`**
   - Text: "We couldn't save the visit. Your entries are kept. Try again or contact your admin."
   - The Previous button goes back to `Visit Details`, with the values kept.
   - The rep doesn't see `{!$Flow.FaultMessage}`.
   - The admin gets it by one of two routes:
     - Logging inside `logVisit` itself, which is my preference.
     - A Send Email element placed before this screen, with its own fault connector going to this screen. That email contains the FaultMessage, the Account Id and the element name.

**Naming and descriptions**
- The flow API name is `Visit_Screen_LogSiteVisit`.
- Give the flow and every element a description.
- There are no hard-coded Ids, users or queues.

## 5. Bulk behaviour

A screen flow handles one interview for one rep, so there is no 200-record case from the flow itself. The risk is inside `logVisit`. It should use `List` input properly, with no SOQL or DML inside a loop. If it creates child records, it shares the 100 SOQL, 150 DML and 10,000 row limits with everything else in the transaction. A governor-limit error rolls back everything even though there's a fault connector.

## 6. Run context and access

- The flow runs in **user context** from a Lightning page, so the rep's object, field and record access applies.
- Reps need the **Run Flows** permission.
- If the flow's access override is on, they must also be in a profile or permission set given access to this flow.
- They need **Apex Class Access** to `VisitService`.
- Put all of that in **one permission set for reps**.
- Apex runs under its own class sharing and access mode. I'd want `with sharing` and `WITH USER_MODE` or `stripInactive`, like `OpportunityService`. Confirm which it uses, because that decides whether reps can log a visit on accounts they can't edit.

## 7. How versions work

- Saving changes to an active flow in Flow Builder is **Save As New Version**. That new version is inactive.
- Only one version is active at a time.
- Activating the new version deactivates the previous one.
- Interviews already running finish on the version they started on.
- The old version stays for rollback.
- When you deploy the flow file, `<status>` decides whether it becomes active. I'd deploy with `<status>Draft</status>`, test it, then activate it.

## 8. Testing, activation, rollback (sandbox only)

Screen flows have no Flow tests, so use Debug and a real user:
1. **Debug** in Flow Builder with an Account. Cover the happy path, a missing required field and a future date.
2. **Force the Apex failure** two ways: `isSuccess = false`, and a thrown exception. Confirm the error screen appears and the entries are kept.
3. **Run it as a test rep**, a user with only the reps' permission set, from the real Lightning page. This proves Run Flows and Apex Class Access are set up.
4. Check the visit record exists, and that existing automation from section 1 behaves as expected.
5. Note the current active version number, then **activate** in the sandbox. For a first version there's nothing to roll back to except deactivating it.
6. If it breaks, activate the previous version or deactivate the flow, and check what the bad version already created.
7. **Production:** a person moves it with a change set and decides about activation there. I'm not planning that.
