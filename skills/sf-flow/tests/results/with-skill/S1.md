What would change the design:
- **An existing after-save Case flow that creates Tasks:** add a path to that flow instead of building a new one, or set an explicit Trigger Order.
- **An Apex trigger that already creates Tasks on close:** the follow-up would be created twice.
- **An active Process Builder process or Workflow Rule that creates the same Task:** plan its migration, and deactivate it when this flow is activated.
- **A required custom field or validation rule on Task:** the Create Records element must populate it, or it will fail.

## Flow type and why

**Record-triggered, after-save (Actions and Related Records).** The flow creates a different record (a Task), and before-save flows can't create other records. It also needs `$Record.Id` for `WhatId`, and that Id isn't available until after the save.

## Assumptions to confirm
- "3 days" means **calendar days**. Business days would need a different formula.
- A Case owned by a **queue** can't own a Task. Assumed: skip the Task and log it (see element 2).
- Cases are never created already closed. If they can be, switch the trigger to "created or updated" with the same condition.

## Element by element

**1. Start (Record-Triggered Flow)**
- **Object:** Case. **Trigger:** A record is updated. **Optimize for:** Actions and Related Records.
- **Condition:** `IsClosed` Equals `{!$GlobalConstant.True}`.
- **Run:** "Only when a record is updated to meet the condition requirements". It fires once when the Case becomes closed, not on later edits of a closed Case. A reopen followed by a re-close fires it again, which is intended.
- **Description:** "Creates a follow-up Task for the Case owner 3 days after the Case closes."

**2. Decision: `Owner Is User`**
- **Outcome `Owner Is User`:** formula `LEFT({!$Record.OwnerId}, 3) = '005'`. Connects to element 3.
- **Default outcome `Owner Is Queue`:** skip the Task and go to element 5b (log, then end). The alternative is assigning it to a fallback user looked up from custom metadata. Nothing is hard-coded either way.

**3. Formula (resource): `fxFollowUpDate`**
- **Data type:** Date. **Value:** `{!$Flow.CurrentDate} + 3`. This is calendar days.

**4. Create Records: `Create Follow-Up Task`**
- **Object:** Task. **How to set fields:** manually.
- **Fields:**
  - `OwnerId` = `{!$Record.OwnerId}`
  - `WhatId` = `{!$Record.Id}`
  - `ActivityDate` = `{!fxFollowUpDate}`
  - `Subject` = `Follow up on closed case ` & `{!$Record.CaseNumber}`
  - `Status` = Not Started
  - `Priority` = Normal
- **Normal connector:** End.
- **Fault connector:** goes to element 5a.

**5a. Fault handling: Send Email `Email Admin – Task Creation Failed`**
- **Chosen design: log and continue.** The Case close still succeeds, and only the Task is lost.
- **Recipient:** an admin address or a public group. Not hard-coded in the flow body.
- **Body includes:** `{!$Flow.FaultMessage}`, `{!$Record.Id}` and the element name `Create Follow-Up Task`.
- **Its own fault connector** goes to End. Without it, a failed email would fail the whole save.

**5b. Queue case: `Email Admin – Queue-Owned Case Skipped`**
- Same pattern as 5a, with its own fault connector to End. An alternative is a log platform event. Skipping silently is not acceptable.

**Descriptions:** every element gets one. Labels are verb plus object.

## Bulk behaviour
A list edit or data load closes up to **200 Cases per transaction**. Each Case runs its own interview, and Salesforce batches the Create Records elements into one DML statement. That is up to 200 Task rows, well under the **150 DML statement** and **10,000 DML row** limits. There is no loop and no query, so SOQL isn't a concern. The limits are shared with every other flow, trigger and process in the transaction, which is why the Step 1 inventory matters. A governor-limit error rolls back the whole transaction, even with fault connectors in place.

## Run context and access
- **Context:** record-triggered flows run in **system context without sharing**. The closing user's permissions don't limit the Task creation.
- **Assignment:** the Task is assigned to the Case owner even if that person can't normally see that Case.
- **Permissions:** no Run Flows permission or Apex class access is needed, because there is no screen and no Apex.

## How versions work
Saving changes to an active flow in Flow Builder creates a **new, inactive version**. Only **one version is active at a time**. Activating a new version deactivates the previous one, while running or paused interviews finish on the version they started on. The old version stays for rollback, so don't delete it. When this flow is first saved there is no previous version.

If you deploy the XML, `<status>` decides whether the version goes live on deploy. Keep it as `<status>Draft</status>` until the tests pass. The file's `apiVersion` is `62.0`.

## Test plan (in `uat`)

Use Flow tests (Flow Builder > View Tests), each with assertions:
1. **Open Case updated to Closed, user owner:** one Task exists, with the right `OwnerId`, `WhatId` and `ActivityDate` of today + 3.
2. **Closed Case edited again (for example, a description change):** no new Task, because the condition isn't newly met.
3. **Case updated but not closed:** no Task.
4. **Queue-owned Case closed:** no Task, and the skip notification is sent.
5. **Forced Task failure** (for example, a temporary required field on Task): the Case still closes and the admin gets the fault email.
6. **Reopen and re-close:** a second Task is created. Confirm that's what you want.

Then debug in rollback mode, then close a few real test Cases. Finally, close **200 Cases** at once with a list edit or data load, and check that there are 200 Tasks.

## Activation and rollback
1. Deploy to `uat` as `Draft`, then run the tests above.
2. Once they pass, activate in `uat` (Setup > Flows > the flow > View Details and Versions > Activate), then smoke-test with real Cases.
3. **Rollback:** note the previously active version number before activating, and activate it again if something breaks. If there isn't one, deactivate the flow. Then check what the bad version already created, since Tasks it made stay.
4. **Production:** a person moves the flow with a change set and decides when to activate it there. I haven't planned or run anything for production.
