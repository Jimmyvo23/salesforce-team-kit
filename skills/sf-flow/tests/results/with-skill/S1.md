What would change the design:
- **An existing Case after-save flow that already creates Tasks or handles closure.** Add a path or Decision outcome to that flow, or give this one an explicit Trigger Order. Don't add a second flow that does the same job.
- **An active Process Builder process or Workflow Rule that creates a Task on close.** Plan its migration. Deactivate it when this flow is activated, or every close creates two Tasks.
- **An Apex trigger on Case or Task that writes Tasks.** Make sure the two don't both write.
- **Validation rules on Task** (for example, a required field). These can block the Task this flow creates.

## 2. Flow type

**Record-triggered, after-save (Actions and Related Records).** The flow creates a record on another object (Task), and before-save flows can't do that.

## 3. Elements

**1. Start**
- **Object:** Case.
- **Trigger:** A record is updated.
- **Optimize for:** Actions and Related Records.
- **Condition:** `IsClosed` Equals `true`.
- **Run when:** "Only when a record is updated to meet the condition requirements". It fires once when the Case becomes closed, not on later edits.
- **Create case:** if Cases can be created already closed, use "created or updated" with `OR(ISNEW(), ISCHANGED({!$Record.IsClosed}))`. I've assumed they can't.
- **Description:** "Creates a follow-up Task for the Case owner when a Case closes."

**2. Decision `Check Owner Is User`**
- A Task owner must be a user, but a Case can be owned by a queue.
- **Outcome `Owner Is User`:** `LEFT({!$Record.OwnerId}, 3) = '005'`. It goes to element 3.
- **Default outcome `Owner Is Queue`:** it goes to element 6, the end, with no Task. This is an assumption. The alternative is a fallback user looked up from custom metadata. Don't hard-code a user Id.

**3. Formula `fxFollowUpDueDate`** (Date)
- `{!$Flow.CurrentDate} + 3`
- This is 3 calendar days. Business days would need a different formula, so please confirm.

**4. Create Records `Create Follow-Up Task`** (one Task, not in a loop)
- **`OwnerId`:** `{!$Record.OwnerId}`.
- **`WhatId`:** `{!$Record.Id}`.
- **`ActivityDate`:** `{!fxFollowUpDueDate}`.
- **`Subject`:** `Follow up on closed case ` + `{!$Record.CaseNumber}`.
- **`Status`:** Not Started.
- **`Priority`:** Normal.
- **Normal connector:** goes to the end (element 6).
- **Fault connector:** goes to element 5.

**5. Send Email `Notify Admin of Task Failure`** (log and continue)
- It sends to an admin address held in a custom label or custom metadata.
- The body includes `{!$Flow.FaultMessage}`, `{!$Record.Id}` and the element name `Create Follow-Up Task`.
- **Fault connector:** goes to the end, so a failed email can't break the save.
- I chose log and continue because a missing follow-up Task isn't worth blocking an agent from closing the Case. If you want a hard block, replace this with a Custom Error element. In that case log with an email or platform event, not a record insert, because the rollback would undo the record.

**6. End**
- Every path ends here.

## 4. Bulk behaviour

A list edit or data load saves up to 200 Cases in one transaction. Each Case runs its own interview. Salesforce batches the Create Records elements, so 200 closed Cases create 200 Tasks in one DML statement. That is far below the 150 DML statement and 10,000 DML row limits. The flow does no Get Records and has no loop. Those limits are shared with every other flow and trigger in the transaction, which is why the inventory matters. The new Tasks also run Task automation and validation rules. A governor-limit error rolls back the whole transaction, even with fault connectors.

## 5. Run context and access

Record-triggered flows run in **system context without sharing**. The closing user's permissions don't limit the Task creation. The Task is owned by the Case owner, whoever closes the Case. No permission set is needed for this flow. Leave How to Run the Flow at its default.

## 6. How versions work

Saving changes to an active flow in Flow Builder creates a new, inactive version. Only one version is active. Activating a new version deactivates the previous one, which stays available for rollback. Running or paused interviews finish on the version they started on. A flow file deployed to the sandbox also creates a new version, and its `<status>` decides whether it goes live. Deploy it as `<status>Draft</status>`, test it, then activate it.

## 7. Testing, activation and rollback (sandbox `uat`)

Testing comes before activation.

**Flow tests** (Flow Builder > View Tests), each with assertions:
1. A Case updated to Closed creates one Task. Check that the owner, `WhatId` and due date (today + 3) are correct.
2. A closed Case edited again creates no new Task.
3. A Case updated but not closed creates no Task.
4. A Case owned by a queue follows the default outcome and creates no Task.

**Real records:**
- **Debug** with rollback mode, then close a few real test Cases.
- **Bulk:** close 200 Cases in one list edit or data load.
- **Fault path:** force a failure, for example with a Task validation rule, and check that the email arrives and the Case still closes.

**Activate:** Setup > Flows > `Case_AfterSave_FollowUpTask` > View Details and Versions > Activate. Do this only after the tests pass. Before activating, note the current active version number. For a brand-new flow there is none, so rollback means deactivating the flow. Rollback means activating the previous version again, then checking what the bad version already changed. Don't delete old versions.

**Production:** a person moves the flow with a change set and decides about activation there.

## 8. Naming

The flow API name is `Case_AfterSave_FollowUpTask`. Elements are named by verb plus object, and each has a description.
