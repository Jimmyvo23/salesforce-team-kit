# Flow: Account Billing Address → Contact Mailing Address

**Type:** Record-Triggered Flow on **Account**, run after the record is saved.

## Trigger
- **Object:** Account
- **Trigger:** A record is updated. Create isn't needed because a new account has no contacts yet.
- **Entry conditions** (Custom Condition Logic: OR): any of these changed, using `ISCHANGED` or "Is Changed = True":
  - `BillingStreet`
  - `BillingCity`
  - `BillingState`
  - `BillingPostalCode`
  - `BillingCountry`
  - Optionally `BillingStateCode` and `BillingCountryCode`, if State/Country picklists are enabled.
- **Optimize for:** Actions and Related Records. It must run after save because it updates other records.

Putting the change check in the entry conditions means the flow only starts when the address changed, not on every account edit.

## Elements

**Option A (recommended): one element, no loop**

1. **Update Records** on Contact:
   - **Filter:** `AccountId` Equals `{!$Record.Id}`
   - **Set fields:**
     - `MailingStreet` = `{!$Record.BillingStreet}`
     - `MailingCity` = `{!$Record.BillingCity}`
     - `MailingState` = `{!$Record.BillingState}`
     - `MailingPostalCode` = `{!$Record.BillingPostalCode}`
     - `MailingCountry` = `{!$Record.BillingCountry}`
     - Use the `...StateCode` and `...CountryCode` fields instead if State/Country picklists are enabled.

Salesforce runs this as one bulk DML statement, so it is bulk-safe and uses a single query and a single DML.

**Option B: explicit loop** (only if you need per-contact logic, such as skipping some contacts)

1. **Get Records:** all Contacts where `AccountId = {!$Record.Id}`, stored as a collection.
2. **Loop** over the collection.
3. **Assignment** inside the loop: set the Mailing fields on `{!currentContact}`, then add it to `varContactsToUpdate`.
4. **Update Records** after the loop, using `varContactsToUpdate`. Keep this outside the loop to avoid DML-in-loop limits.

## Error handling
- Add a **Fault path** from the Update Records element. It can create a log record or send an email to an admin, so a failed contact update (validation rule, lock, etc.) doesn't fail silently.

## Considerations
- **Recursion:** Updating Contacts doesn't re-trigger the Account flow, so there's no loop risk.
- **Volume:** Accounts with more than 10,000 contacts hit the DML row limit. For those, add an **Asynchronous (Scheduled) Path** to run the update after the transaction.
- **Opt-out:** If some contacts should keep a custom mailing address, add a checkbox such as `Keep_Custom_Mailing_Address__c` and add `= False` to the Contact filter.
- **Contact validation rules:** Rules that require fields the flow doesn't set can block the update, which is why the fault path matters.
- **Testing:** Test with an account that has 0, 1 and about 200 contacts, and test changing only one address field.
