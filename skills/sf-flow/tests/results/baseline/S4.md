# S4: Screen flow with Apex (baseline)

`VisitService` isn't in this project. The only Apex class is `OpportunityService`, and nothing references `logVisit`. I don't know the real `@InvocableMethod` signature, so the design below uses assumed inputs and outputs. I haven't written any flow metadata.

## Design: `Log_Site_Visit` (Screen Flow)

**Entry points**
- Quick action on Account (and Lead, if reps visit prospects). The flow receives `recordId`, which becomes the visit's target.
- It can also be added as a utility bar item or a Lightning page component for mobile use.

**Screens**
1. **Visit details**
   - Account (pre-filled and read-only when launched from a record, otherwise a lookup)
   - Visit date/time (defaults to now, can't be in the future)
   - Visit type (picklist: Intro, Demo, Follow-up, Support)
   - Contacts met (multi-select lookup, filtered to the account)
   - Notes (long text, required)
   - Next step and due date (optional)
2. **Confirm**: a read-only summary with Back and Submit buttons.
3. **Result**: a success message with a link to the created record, or an error message with a Back button.

**Logic**
- A **Decision** after screen 1 checks that the date isn't in the future and that notes aren't blank. Failures return to screen 1 with an error. Screen-level validation formulas handle most of these checks.
- An **Action** element calls `VisitService.logVisit`. Its fault connector goes to the error screen and shows `{!$Flow.FaultMessage}`. It never ends silently.
- An optional **Get Records** before the action looks up the Account owner and name for the confirm screen.

**Assumed Apex contract** (please confirm or correct)
- Inputs: `accountId`, `visitDate`, `visitType`, `contactIds` (list), `notes`, and optionally `nextStep` and `nextStepDate`.
- Output: `visitId` (or a success flag plus a message).
- Invocable methods take a `List<Request>` and return a `List<Result>`. The flow passes a single-item collection through a Request Apex-defined variable, or the individual fields, depending on how the class is built.

**Design points**
- Put all business logic and DML in Apex, and keep the flow to UI and validation.
- Don't use a Create Records element as a fallback, so there's a single write path.
- Apex should run `with sharing` and `WITH USER_MODE`, like `OpportunityService`, so reps' field permissions apply.
- Add the flow to the reps' permission set and give them access to the Apex class.
- Mobile: use only standard screen components, so the flow works in the Salesforce app.
