**Before it will work, an admin needs to set up three things in the sandbox:**
- **Named Credential `ERP`:** URL `https://erp.example.com`, with an External Credential for authentication. The endpoint stays out of the code and the class calls `callout:ERP/api/orders`.
- **External Credential access:** a permission set that grants the External Credential principal to the users whose transactions run the job.
- **Two custom fields on Order:** `ERP_Sync_Status__c` (text or picklist: Pending, Sent, Failed) and `ERP_Last_Error__c` (text, 255). Users need field access to both, because the job saves with `update as user`.

`classes/OrderTriggerHandler.cls`:
```apex
public with sharing class OrderTriggerHandler {
    public static final String STATUS_PENDING = 'Pending';

    // Marks Orders that need sending as Pending, so none is lost if the job can't be enqueued.
    public static void beforeSave(List<Order> orders, Map<Id, Order> oldMap) {
        for (Order o : orders) {
            if (needsSync(o, oldMap)) {
                o.ERP_Sync_Status__c = STATUS_PENDING;
            }
        }
    }

    // One enqueue per transaction, never per record.
    public static void afterSave(List<Order> orders, Map<Id, Order> oldMap) {
        Set<Id> ids = new Set<Id>();
        for (Order o : orders) {
            if (needsSync(o, oldMap)) {
                ids.add(o.Id);
            }
        }
        if (!ids.isEmpty()) {
            System.enqueueJob(new OrderErpSyncJob(ids));
        }
    }

    // Insert: always send. Update: only when Status really changed. The job only writes the ERP_*
    // fields, so its own update does not match this filter and the trigger can't loop.
    @TestVisible
    private static Boolean needsSync(Order o, Map<Id, Order> oldMap) {
        return oldMap == null || o.Status != oldMap.get(o.Id).Status;
    }
}
```

`triggers/OrderTrigger.trigger`:
```apex
trigger OrderTrigger on Order (before insert, before update, after insert, after update) {
    if (Trigger.isBefore) {
        OrderTriggerHandler.beforeSave(Trigger.new, Trigger.oldMap);
    } else {
        OrderTriggerHandler.afterSave(Trigger.new, Trigger.oldMap);
    }
}
```

`classes/OrderErpSyncJob.cls`:
```apex
public with sharing class OrderErpSyncJob implements Queueable, Database.AllowsCallouts {
    public static final Integer TIMEOUT_MS = 10000;
    private static final Integer MAX_PER_JOB = 10;   // 10 x 10 s = 100 s: under the 120 s cumulative callout limit

    @TestVisible
    private static Boolean chainRemaining = true;    // tests switch this off to keep to one job

    private final Set<Id> orderIds;

    public OrderErpSyncJob(Set<Id> orderIds) {
        this.orderIds = orderIds;
    }

    public void execute(QueueableContext ctx) {
        List<Id> batch = new List<Id>();
        Set<Id> rest = new Set<Id>();
        for (Id i : orderIds) {
            if (batch.size() < MAX_PER_JOB) {
                batch.add(i);
            } else {
                rest.add(i);
            }
        }

        List<Order> results = new List<Order>();
        for (Order o : [SELECT Id, OrderNumber, Status, TotalAmount, AccountId, EffectiveDate
                        FROM Order WHERE Id IN :batch WITH USER_MODE]) {
            results.add(OrderErpService.send(o));    // callouts first, no DML yet
        }
        update as user results;                      // then one DML with the outcome

        if (!rest.isEmpty() && chainRemaining) {
            System.enqueueJob(new OrderErpSyncJob(rest));
        }
    }
}
```

`classes/OrderErpService.cls`:
```apex
public with sharing class OrderErpService {
    // The Named Credential "ERP" holds the base URL and authentication.
    private static final String ENDPOINT = 'callout:ERP/api/orders';

    // Posts one Order and returns an Order carrying only the outcome fields. The caller saves it.
    public static Order send(Order o) {
        HttpRequest req = new HttpRequest();
        req.setEndpoint(ENDPOINT);
        req.setMethod('POST');
        req.setHeader('Content-Type', 'application/json');
        req.setTimeout(OrderErpSyncJob.TIMEOUT_MS);
        req.setBody(toJson(o));

        Order result = new Order(Id = o.Id);
        try {
            HttpResponse res = new Http().send(req);
            Boolean ok = res.getStatusCode() >= 200 && res.getStatusCode() < 300;
            result.ERP_Sync_Status__c = ok ? 'Sent' : 'Failed';
            result.ERP_Last_Error__c = ok ? null : (res.getStatusCode() + ' ' + res.getBody()).left(255);
        } catch (CalloutException e) {               // timeout or connection error
            result.ERP_Sync_Status__c = 'Failed';
            result.ERP_Last_Error__c = e.getMessage().left(255);
        }
        return result;
    }

    @TestVisible
    private static String toJson(Order o) {
        return JSON.serialize(new Map<String, Object>{
            'salesforceId' => o.Id,
            'orderNumber' => o.OrderNumber,
            'status' => o.Status,
            'total' => o.TotalAmount,
            'accountId' => o.AccountId,
            'effectiveDate' => o.EffectiveDate
        });
    }
}
```

**How it works**
- **Trigger and handler:** the trigger body only calls the handler. Inserts always send, and updates send only when `Status` changed. The before trigger marks those Orders `Pending`, and the after trigger enqueues one Queueable with all their Ids.
- **Queueable job:** it handles 10 Orders per job, so 10 callouts at a 10-second timeout stay under the 120-second callout limit. Any remainder is chained into a new job. It makes all its callouts first, then saves the outcomes with one `update as user`.
- **Callout service:** it POSTs the Order JSON to `callout:ERP/api/orders`. A 2xx response sets the status to `Sent`. Anything else, or a timeout, sets `Failed` and stores the status code and body in `ERP_Last_Error__c`.
- **No loop:** the job only writes the `ERP_*` fields, so its own update doesn't pass the `Status` filter and doesn't re-enqueue.
- **Security:** every class is `with sharing`, queries use `WITH USER_MODE`, and DML uses `as user`. Nothing runs in system mode.

**Things to know**
- **Payload:** it sends header fields only (Id, OrderNumber, Status, TotalAmount, AccountId, EffectiveDate). If the ERP needs Order lines, tell me its schema and I'll add them.
- **Retries:** there is no automatic retry yet. `Failed` and `Pending` Orders stay visible by status. A scheduled job could re-send 5xx and timeout failures with a retry cap, but not 4xx. I can add that.
- **Async triggers:** if Order saves can also happen inside a Queueable, batch or future (where only one `enqueueJob` is allowed), the `Pending` marker keeps those Orders recoverable.
- **Tests:**
  - The mocked-callout tests need the `ERP_*` fields to exist. They also depend on your org's required Order fields and validation rules. If inserting a `Draft` Order fails, adjust `newOrders`.
  - The two handler tests call the handler directly with in-memory Orders, so they don't depend on activation rules.
  - I haven't verified that the first chunk of 10 is the same 10 in the 200-record test, so that test only asserts counts.
