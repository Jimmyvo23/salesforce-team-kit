# S1: Review a class (baseline)

**Verdict: request changes.** I couldn't find a T-012 spec anywhere in the project, so I reviewed the code on its own merits and can't check it against the task's requirements.

**Blocking issues** (`DiscountJob.cls`)

1. **SOQL in a loop (line 4).** This runs one query per opportunity. Apex allows 100 synchronous queries per transaction, so a batch of more than 100 opportunities throws `System.LimitException: Too many SOQL queries`. Collect the `AccountId`s first, then run one query into a `Map<Id, Account>`.
2. **DML in a loop (line 7).** This runs one `update` per qualifying record. It will hit the 150 DML statement limit and fires triggers and flows once per record. Collect the changed records in a list and update them once after the loop.
3. **Unhandled null or missing account (line 4).** `[SELECT ... WHERE Id = :o.AccountId]` throws `QueryException` ("List has no rows") if `AccountId` is null or the account isn't visible. Any opportunity without an account will fail the whole job. Using the map with `get()` and a null check avoids this.
4. **Hardcoded record type ID (line 5).** `'012000000000ABC'` differs between orgs and sandboxes, and it looks like a placeholder. Resolve it with `Schema.SObjectType.Opportunity.getRecordTypeInfosByDeveloperName().get('...').getRecordTypeId()`.

**Smaller points**

- **Self-update on the input records:** Calling `update o` on records passed in is fine in a standalone job. If `apply` is ever called from a before-trigger, the update is redundant and can cause recursion.
- **Magic number:** `10` is hardcoded. Use a constant or custom metadata.
- **No error handling:** `update` is all-or-nothing. Consider `Database.update(list, false)` and log the failures.
- **Sharing and security:** The class has no sharing declaration. Add `with sharing` or `inherited sharing` deliberately. Consider `WITH USER_MODE` on the query as well.
- **Naming:** `DiscountJob` suggests Batch or Queueable, but the class implements neither interface. It's just a static helper.
- **Tests:** I found no test class for it. Add one that covers a bulk case of at least 200 records, a null account, a non-partner account, and a wrong record type.

**Suggested shape**

```apex
public with sharing class DiscountJob {
    public static void apply(List<Opportunity> opps) {
        Set<Id> accountIds = new Set<Id>();
        for (Opportunity o : opps) {
            if (o.AccountId != null) accountIds.add(o.AccountId);
        }
        Map<Id, Account> accounts = new Map<Id, Account>(
            [SELECT Id, Type FROM Account WHERE Id IN :accountIds]);

        Id partnerRtId = Schema.SObjectType.Opportunity
            .getRecordTypeInfosByDeveloperName().get('Partner').getRecordTypeId();

        List<Opportunity> toUpdate = new List<Opportunity>();
        for (Opportunity o : opps) {
            Account a = accounts.get(o.AccountId);
            if (a != null && a.Type == 'Partner' && o.RecordTypeId == partnerRtId) {
                o.Partner_Discount__c = 10;
                toUpdate.add(o);
            }
        }
        update toUpdate;
    }
}
```
