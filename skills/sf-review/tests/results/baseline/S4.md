# S4: Automation overlap (baseline)

**Review of T-012: the flow as designed won't work, because the existing trigger overwrites it.**

`force-app` already has `OpportunityTrigger.trigger:3`. It runs on before insert and before update, and sets `Partner_Discount__c = 5` for every Opportunity where `Type == 'Renewal'`.

1. **The trigger overwrites the flow's value.** Before-save record-triggered flows run before before-triggers in the order of execution. The flow would set 10, then the trigger would set 5 on the same record. Partner renewals would end up at 5, and nothing would error.
2. **The two rules conflict.** The trigger gives 5 to all renewals, including partner ones. The flow gives 10 to partner renewals. The business rule needs to be settled first: is it 5 for non-partner renewals and 10 for partner renewals, or is 10 meant to replace 5?
3. **The trigger overwrites manual edits.** It reassigns the value on every update of a renewal, not just on insert or when the type changes. A flow that only fires on create or on a change to `Type` would behave differently from the trigger. The same logic should not be implemented in both places.
4. **Nothing in the repo identifies a partner renewal.** `force-app` has no partner flag, no record type and no Account field. The flow's entry criteria can't be checked until that is defined.
5. **The flow isn't in `force-app` yet.** There are no flow metadata or tests for the trigger, so I couldn't review the flow's own logic.
6. **The unit is probably fine.** `Partner_Discount__c` is a Percent field (precision 5, scale 2), so the value 10 means 10%. Confirm that's the intent.

**Recommendation:** Keep the logic in one place.
- **Flow:** Move the whole rule into `Renewal_Discount`, with 10 for partner renewals and 5 for other renewals if that is still wanted. Then remove the `Type == 'Renewal'` line from the trigger, or delete the trigger if nothing else is in it.
- **Trigger:** Alternatively, extend the trigger with the partner condition and drop the flow. That keeps one automation and avoids order-of-execution surprises.

I'd go with the flow if the team prefers declarative changes, as long as the trigger line is removed in the same deploy.
