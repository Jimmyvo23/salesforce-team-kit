# S4: Automation overlap (with-skill)

**Verdict: Changes needed** — T-012 (design review)

1. **Blocking** — `force-app/main/default/triggers/OpportunityTrigger.trigger:3` — Automation overlap. The existing before-insert/before-update trigger already writes `Partner_Discount__c` (set to 5 when `Type == 'Renewal'`). The new Renewal_Discount flow would be a second writer on the same field. A before-save flow runs first (step 3) and a before trigger runs after it (step 4). So **the trigger overwrites the flow**, and every Renewal gets 5, not 10. The flow's 10 would never persist for any record the trigger matches. The design also doesn't say what a "partner renewal" is. The trigger keys on `Type == 'Renewal'` and has no partner condition. Fix: keep one place for this rule. Either:
   - (a) Put the 10-for-partner-renewals rule in the existing trigger. Move the logic into a handler class and branch on partner vs. non-partner renewals. Don't build the flow.
   - (b) Build the flow, with the 5 rule moved into it, and retire the trigger's write to this field.

   Either way, ask the Architect to confirm the intended values: 10 for partner renewals and 5 for other renewals, or whether the 5 should go away.
2. **Blocking** — Missing flow design. There is no flow metadata in `force-app/` yet, so I can't check fault paths (item 6) or whether the flow has any Get/Update elements inside a loop (item 3). A before-save flow should assign the field directly on `$Record` with no DML. Confirm that in the design.
3. **Blocking** — Missing rollback plan (item 9). There is no Work Order or handoff. Fix: write the rollback in the Work Order. For example, deactivate the flow or revert the trigger, and say whether records already saved with the new value need a data fix.
4. **Blocking** — Tests (item 7). None exist. Whichever option is chosen, require these:
   - Asserts that query the records and check `Partner_Discount__c == 10` for a partner renewal.
   - A bulk case of 200+ Opportunities in one call.
   - A negative case: a non-partner renewal and a non-renewal, asserted unchanged (or still 5 where the trigger applies).
   - A restricted user via `System.runAs`, if access is touched.
   - A test that covers records matching both rules, so the winner is asserted explicitly.
5. **Should fix** — `OpportunityTrigger.trigger:3` — The hard-coded 5 (and the new 10) are business rates. Move them to Custom Metadata. This is not a blocker. Also, the trigger has no handler class, so adding logic there is a good moment to introduce one.
6. **Note** — The repo is not the org. Other flows, workflows or triggers may write `Partner_Discount__c` in the org. Run the automation inventory queries from sf-architecture against the `uat` sandbox before building.
7. **Note** — I didn't check `sourceApiVersion` or the class `apiVersion`. `sfdx-project.json` is not in the project, and `OpportunityService.cls` has no CRUD/FLS issue visible (`with sharing`, `WITH USER_MODE`).
