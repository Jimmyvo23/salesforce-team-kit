# S3: Static analysis (with-skill)

Before I approve T-012, I do three things: read the context, run Code Analyzer, and go through a 10-item checklist. I haven't looked at the T-012 code yet, so this describes the process and not a verdict.

**1. Read the context**
- I read `docs/stories/T-012.md`, the Work Order, the `.team/handoffs/T-012-*.md` files and the branch diff.
- I check `sourceApiVersion` in `sfdx-project.json` and the `apiVersion` in each class's `-meta.xml`, because the version decides the Apex security defaults.
- If any of these files are missing, I still review the code and give a verdict. I list what's missing, because I can't check the change against the acceptance criteria or the rollback plan without them.

**2. Code Analyzer**
```
sf code-analyzer run --target <changed files> --severity-threshold 2 --view detail
```
- Critical (1) and High (2) violations always block.
- Moderate (3) blocks if it's a Security rule or a limits-in-loop rule on changed lines.
- Low and Info are notes only.
- If I can't run it, I give you the exact command and say it hasn't been run. I can't approve until it has run clean.

**3. Checklist**

| # | Check | Blocks? |
|---|---|---|
| 1 | CRUD/FLS: `WITH USER_MODE` on SOQL, `as user` on DML | Yes |
| 2 | Sharing keyword on every class | Yes |
| 3 | SOQL or DML inside a loop, in Apex or in a Flow Loop | Yes |
| 4 | Hard-coded Ids, URLs or credentials | Yes (hard-coded business numbers are Should fix) |
| 5 | Automation overlap: another trigger, flow or class writing the same field | Yes |
| 6 | Flow fault paths | Yes |
| 7 | Tests that assert behaviour | Yes |
| 8 | Callouts through Named Credentials only, none synchronous in a trigger | Yes |
| 9 | Rollback plan written down | Yes |
| 10 | Scope creep (about 25% more than the Work Order, or new objects) and real customer data | Yes |

- **Overlap (item 5):** I grep `force-app/` for each field the change writes. If a before trigger and a before-save flow both write the field, the trigger wins. I'd still ask for a single place for the rule. The org may hold automation that isn't in the repo.
- **Tests (item 7):** Coverage alone doesn't count. I require four things:
  - asserts on expected values
  - a bulk case of 200+ records
  - a negative case showing records that must not change
  - a `System.runAs` restricted-user test when the change touches access

**Verdict:** The result is either **Approved** or **Changes needed**. Each issue gets its own note with `file:line`, what's wrong and the fix. One Blocking note means Changes needed. I don't edit files, and tests only run in the sandbox org.
